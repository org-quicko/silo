# Repo map

> Where everything lives. The rules that shape it are in
> [code-design.md](code-design.md).

## The workspace

```
silo/
├─ apps/
│  ├─ server/                 @silo/server — the CLI, HTTP API, core and adapters
│  └─ admin/                  @silo/admin  — the React admin UI
├─ packages/
│  ├─ shared/                 @silo/shared — runtime-neutral logic both sides need
│  └─ create-silo-plugin/     the published plugin scaffolder
├─ plugins/                   first-party plugins, one workspace package each
│  └─ silo-plugin-strapi-import/  a Strapi 5 SQLite import — entries and media — with its own admin panel (D41)
│     ├─ src/                     index.ts, then routes/ worker/ strapi/ staging/ silo/ panel/ types/
│     └─ test/                    one file per subject, with support/ holding the synthetic export
├─ tools/                     build, packaging, seeding and version tooling
├─ packaging/                 Homebrew formula template and RPM inputs
└─ docs/                      context/ (what is) and design/ (why)
```

One Bun workspace, one install root, one `bun.lock`. The root `package.json`
holds no runtime dependencies — it declares the members and delegates every
script.

## Root files

| Path | What it is |
|------|------------|
| `package.json` | Workspace root. Its `version` is the single source of truth (D28) — the binary, the archives, the RPM and the Homebrew formula all derive from it, and the release workflow refuses a tag that disagrees |
| `tsconfig.base.json` | Compiler options shared by every Bun-side package |
| `tsconfig.json` | One typecheck pass over the server, `shared` and `tools` |
| `CONTEXT.md` | Current state, and the index into `docs/context/` |
| `IMPLEMENTATION.md` | Vision, the D1–D54 decisions log, and the index into `docs/design/` |
| `CLAUDE.md` | Standing instructions for AI assistants |
| `silo.toml` | A commented example config; every key is optional |
| `Dockerfile` | Two stages — build the admin UI, then a runtime image with only the server's dependencies. Its `COPY` list must name every workspace manifest, or `bun install` aborts with "Workspace not found" |
| `.gitattributes` | `* text=auto eol=lf`. What it fixes is the *working tree* on Windows, where `core.autocrlf=true` would otherwise check the repo out as CRLF and break the byte-for-byte drift test between the scaffolder's `silo-api.d.ts` and the host's copy |

## `apps/server/src/`

| Directory | What it holds |
|-----------|---------------|
| `cli/` | `Cli` parses argv, `CliOptions` owns the flag table, `UsageText` the help, `CommandRouter` routes in three tiers, and `commands/` is one class per subcommand. The config file itself is chosen by `CliOptions.configPath`: `--config`, then `SILO_CONFIG`, then `silo.toml` beside the process (D50). `runtime/silo-runtime.ts` does the dependency wiring |
| `config/` | `Config` and its sub-shapes, `ConfigLoader`, `ConfigScaffold` (the annotated default file, written by `silo init` and by an install that has no file to list a plugin in), and the two editors of a live `silo.toml`: `PluginBlockWriter`, which appends and removes a `[[plugins]]` entry rather than re-serialising, and `BlobStorageTable` (D45), which reads and replaces the `[blob_storage]` table. Both edit text and parse the result before writing it, refusing any edit that would have changed anything else |
| `core/domain/` | `Entry`, `Scope`, `Collection`, `Meta` and their helpers, plus D51's three record shapes — `project-record.ts`, `environment-record.ts`, `collection-record.ts` — and `system-collections.ts`, which names silo's own seven collections once so both adapters seed the same set. `SystemCollections.isKnown` is deliberately **not** the same question as `EntryUtils.isSystemCollection`: the latter asks whether a name is `_`-prefixed and reserves the whole namespace, and stays the security boundary |
| `core/ports/` | `Storage`, `BlobStorage`, `DerivedIndex` — interfaces only, importing no adapter |
| `core/services/` | The application service layer. `SiloService` is the facade; `scopes`, `collections`, `entries`, `search`, `keys`, `plugins`, `audit`, `transfer`, `media` and `renames` are the services behind it. `rename-service.ts` (D51) owns the *order* a rename happens in — refuse, plan the claim cascade, check the `silo.toml` half, rename the record, cascade, restart any plugin whose grant moved, audit — as one service rather than a method on each of the three, since that order is the hard part and is the same every time. `support/scope-rename-cascade.ts` is the claim rewrite it drives, staged behind a `_scope_renames` marker that doubles as a name reservation. `support/` holds what they share — the `ServiceContext`, the schema cache, the write lock. `media/` holds **two** staged sagas, both because the operation spans more than one adapter write and no `Storage` method can make it atomic: `media-deletion-service.ts` stages `state: "deleting"` on one record (D23), and `media-folder-move-service.ts` stages a `_media_folder_moves` marker naming `from` and `to` (D49). Both are replayed at startup from `serve-command.ts`, and both count failures rather than throwing, so neither can stop the server booting |
| `core/errors/`, `core/query/`, `core/schema/`, `core/keys/`, `core/media/`, `core/search/`, `core/transfer/`, `core/hooks/`, `core/plugins/`, `core/audit/` | One subject each. `core/plugins/` is the grant record and its rules (D34) — the store-side half of plugin authority, including the config override a running instance may be given (D39), which `plugins/` reads but does not own. `core/audit/` is the authority-change trail (D38): the event shape, the actor, and the closed list of actions. `core/transfer/`'s `Exporter` has two output shapes for the one archive: a path, which `tar.c` writes itself, and `exportTarGzStream`, which gzips into a `ReadableStream` and owns the temp tree until that stream ends — an archive holds a copy of every media byte, so the response used to cost as much memory as the media library. `Importer` mirrors it: a path, a `Buffer`, and `importTarGzStream`, which pumps a stream into `tar.x` and finishes on the `end` tar emits only once its pending writes are done — so the walk never sees a half-extracted tree, and a truncated upload fails with the gzip error rather than a missing `manifest.json` |
| `adapters/storage/sqlite/` | The indexed adapter, split per table: migrations, meta, scopes, **collections** (`sqlite-collection-store.ts`, which replaced `sqlite-schema-store.ts` when `collections` replaced the `schemas` table — D51), entries, media references, FTS documents, and the compiler and searcher on top. `sqlite-scope-resolver.ts` is the one place names meet ids, forwards only and cached whole; `sqlite-record-mapper.ts` maps the three record tables' rows; `sqlite-id-claim.ts` holds the rule for an id an importer supplied; `sqlite-connection.ts` is the handle every one of them holds instead of the raw `Database`, owning an unbounded cache of the statements prepared against it so that `close()` can finalize them all and actually release the file |
| `adapters/storage/fs/` | The plain-files adapter, split the same way, with `FsLayout` holding the on-disk path grammar that *is* the export format (D5) — still keyed by **name**, because the tree is meant to be read by a human, with the record ids in the markers `fs-marker.ts` reads and writes. `fs-collection-store.ts` replaced `fs-schema-store.ts` and owns the one rename that is not a single syscall: the destination marker carries `moving_from` and `resumePending` finishes the move at the next open (D51). `fs-system-seed.ts` is `SqliteMigrations.seedSystemRecords`' counterpart, so both adapters answer `listCollections(Scope.System)` alike. There is deliberately **no** name-to-id cache here, where SQLite has one |
| `adapters/blob/` | Filesystem and S3 blob stores |
| `adapters/http/` | The outbound client used by server-to-server copy. `exportArchiveStream` hands the source's archive back as a stream, peeking its first chunk to keep the empty-archive check and putting that chunk back — the destination would otherwise buffer whole what the source just streamed |
| `http/` | `SiloServer` builds the Hono app; `routes/` is one class per route group — `MediaStorageRoutes` (D45) and `MediaFolderRoutes` (D49, `/api/media/folders`'s list/create/rename-move/delete-recursive) both register before `MediaRoutes` so `storage` and `folders` are never read as an asset id; `MediaDeleteBatch` and `MediaInUseDetails` are the per-id outcome loop and the claim-filtered "still in use" facts, factored out of `MediaRoutes` because bulk delete, recursive folder delete and purge all need the same two things (D49) — including `ExtRoutes`, the single handler every plugin route is matched and dispatched through (D36) — `auth/` the claim helpers, including `RouteAuth.requireForcedMediaDelete` (D49), the one `async` because a media force's reach is data-derived rather than read off the route, and the injected-principal slot a plugin dispatch arrives in (D35), `middleware/` logging and auth — where `LoggingMiddleware` since D52 also records one bounded metric per `/api/` request, on the same timer as the access log but switched independently of it, and `ObservabilityRoutes` is the one route that reads them back. `TransferRoutes` returns `/api/export` as a stream rather than a body it has read, which is why it holds no temp file of its own, and takes `/api/import`'s body as one; its multipart branch stays for callers posting a form, but only the raw branch truly streams, since a part cannot be found without parsing the body around it |
| `logging/` | `Logger`, the level union, the `LogSink` port and its console/file implementations, and the two read-side helpers. Nothing here knows about HTTP or storage |
| `observability/` | The process-local metrics accumulator behind `GET /api/observability` (D52). `Observability` is the facade the server holds one of; `RequestMetrics` owns the process-lifetime counters, the per-endpoint table and the rolling sixty-minute chart, `LatencyHistogram` the fixed-boundary distribution beneath both, and `StorageMetrics` the cached background directory and filesystem probes. Everything here is **bounded on purpose** and the bounds are the design: series keys are Hono's registered route pattern so no id or query becomes a series, endpoints collapse into one `* <other>` row past 256, the chart prunes to sixty minutes, a percentile is a bucket bound clamped to the observed maximum, and a directory walk skips the media subtree, follows no symlink and stops at 50,000 entries. Nothing here reads content, a caller or a path. Import from `observability`, never a file inside |
| `plugins/` | Six submodules with an index each — `manifest/` reads what a plugin declares without running it: since D36 that is a `contributes` block (hooks, routes, a `runtime`, providers — none of them exclusive) and a `permissions` block splitting `required` from `optional` with a reason for each, read by one small reader per block so no file owns two grammars — `contract/` describes the client a plugin is handed and emits both halves of it (D35), `host/` executes it, `runtime/` is what it can see and do, plus the `PluginApiDispatcher` its `ctx.fetch` lands in and the `PluginRouteTable` a request is matched against (D36), `registry/` is the single wiring site and, since D39, the live one — `PluginRegistry` is a mutable ordered set that only `PluginSupervisor` mutates, with `PluginLifecycle`, `PluginConfigurator`, `PluginRescan`, D42's `PluginInstallation`, D43's `PluginUninstallation` and the read-only `PluginInspector` beside it — and `install/` acquires it. `PluginInstallation` and `PluginUninstallation` are the two places that *write* `silo.toml`: the first holds the order an install happens in (refuse before fetching, refuse before running, spawn ungranted, grant, list last) and the rule that the block it appends carries `claims = []`, because only the record half of a grant is checked and revocable; the second holds that order reversed (un-list first and fail hard, stop, forget the record and its key, delete the files last and forgive it), because a block naming a package that is gone fails the whole process rather than that plugin. `manifest/` also owns D41's two additions — a route's declared `body` contract, and `contributes.ui`, whose panel `registry/plugin-panel.ts` reads off disk for the one route that serves it. Import from `plugins`, never a file inside |
| `settings/` | Settings an operator changes through the API rather than by editing a file (D45, D46). Two subjects, one shape, which is what the directory is named for: a pure half that decides which value wins, and a supervisor that writes one table of `silo.toml` and applies the result live. `MediaStorageSettings`/`MediaStorageSupervisor` own `[blob_storage]` — parse a body, merge over *the file* so an env-held secret is never copied into it, check the driver, write, re-read the config the way a start reads it, open the store from that, swap it in, and put the file back if any of it fails. `MediaPolicySettings`/`MediaPolicySupervisor` own `[media]` the same way: where media URLs point and what the library accepts. Separate because a bucket that will not open must not hold up a correction to the allowlist. `ConfigSectionSettings`/`ConfigSupervisor` (D47) cover the rest of the file, driven by the `ConfigSections` spec rather than hand-written, and are the first pair that cannot always apply what they save: they keep the config the process *started on* separate from the file and report the difference as a restart owed. `ConfigFileAccess` (D50) is what all three ask before reporting a form writable, and what wraps every write: it probes the path rather than the fact of having been given one, and turns a filesystem refusal into a `400` naming the path instead of a `500` naming nothing. Import from `settings`, never a file inside |
| `runtime/` | Process lifecycle: the run file that records a live server, the daemon mechanics, the listen-address grammar, and the process title |

## `apps/admin/src/`

| Directory | What it holds |
|-----------|---------------|
| `api/` | `SiloApi` is the facade; `clients/` is one class per resource, `transport/` holds the one place a request is made, `types/` the DTOs |
| `claims/` | `ClaimGroups` (a claim set → the handful of sentences it means) and `ClaimWords` (the vocabulary it reads them in). Used by the key form and the plugin grant screen, which is why it is not inside either |
| `components/` | Shared visual primitives, grouped by kind: `modal/`, `buttons/`, `feedback/`, `data/`, `brand/`, `controls/`, `navigation/`. `feedback/` holds the app's one waiting state (D53): `Spinner` is the ring — the theme's own `--line-2` track and `--accent` arc, with `prefers-reduced-motion` answered in the one place — and `LoadingState` pairs it with the sentence naming what is being waited for, `fill` centring in the viewport for a state that *is* the screen |
| `forms/` | The RJSF theme — `templates/`, `widgets/`, `fields/` — plus the two pure files that decide what it draws. `build-ui-schema.ts` picks widgets, reading types through `SchemaType` and descending into an array's `items` as well as an object's `properties`: every imported property is `["object", "null"]`, so a comparison against `'object'` stopped the walk at the first nested component and the media fields inside one rendered as text boxes. `form-schema.ts` marks a property that declares *nothing* with the JSON widget — RJSF returns `null` for a keyword-less schema before `ui:field` is read, so `{}` (a Strapi `json` column, and what the `any` kind saves) was not rendered at all. `templates/NestingDepthContext.ts` is how deep a template sits — RJSF hands one no notion of its own position in the tree — incremented by a labelled object group and by an expanded array item, and published to CSS as `--nest-depth` so a card's surface and a group's rail step one shade lighter per level |
| `query/` | `FilterModel` (the builder's flat model ↔ the Query AST), `UrlFilter` (its round trip through the address bar), `PathLabel` |
| `router/` | The client router and its route table |
| `schema/` | `SiloRefs` prepares a schema for RJSF — which follows only internal `#/…` pointers — by embedding what a `silo://` ref names under `$defs` and rewriting the ref, falling back to a raw-JSON marker for a remote URL, an unknown target or a cycle. Since D54 what it embeds comes from the **document's own `$defs`**, which the server bundles and re-bundles on read, so rendering one entry costs one schema rather than every schema in the scope. `SchemaDraft` (a JSON Schema document ↔ the visual builder's field list), `SchemaType` (what type a property declares, read as the *union* JSON Schema allows — `type` is a string or an array of them, and `["integer", "null"]` is what every imported nullable field carries, so a reader comparing it to `'integer'` is false for exactly the fields real content has; `of` gives the single named type, `isNullable`, `isUntyped` and `isUnresolved` the rest, and the three are total over the keyword so no reader needs a fallback). `SchemaDraft` is the only writer of those two, and the one place the round trip can lose something: `build` rewrites `type` from the field's kind, so nullability rides on `SchemaField.nullable` rather than on the `raw` spread it overwrites, a typeless property is the `any` kind and stays typeless, and an array form naming other than one real type joins `oneOf`/`anyOf`/`allOf` as a `construct` — left intact for Code view, because no one control draws two types. An enum carries nullability twice, in `type` and as a `null` member of `enum`, and both are rebuilt from the one flag: writing only the first gives a field whose type permits a null its own `enum` refuses |
| `store/` | The admin's server state (D53). `store.ts` is `Store` and the singleton over it — a `ResourceState` per cache key, one request per key in flight, an epoch per key so a read settling behind a write cannot put the pre-write answer back, and `invalidate`/`invalidatePrefix`/`set`/`clear` as the ways it is moved. `store-keys.ts` spells every key once, rooted at the *saved connection's* id rather than the server URL, because two saved servers can address one instance with different API keys and a key's claims decide what an answer contains. `use-resource.ts` is the hook every read site uses: `useSyncExternalStore` for the value, a dispatch from an effect for the refresh, and `staleAfter`/`keepPrevious`/`watch` as its three options. Above them sit the resource hooks — `use-session.ts`, `use-collections.ts` (counts included since D54, so there is no per-collection count hook any more), `use-collection-schema.ts` for the one collection a page draws — one key per collection, so the entries list warms it and every entry opened out of that list is a cache read — `use-collection-schemas.ts` for all of them, which since D54 has exactly one caller, the search bar's field-name matching, and `use-entry.ts`. `store.test.ts` covers the properties the rest depends on, the epoch included |
| `styles/` | The intentionally global CSS foundation |
| `utils/` | `Formatters`, `ThemeManager`, `ScopeMemory`, `CollectionVisits`, `ScrollMemory` (where the reader had scrolled to, per view URL, for this session only — in memory rather than in storage, because a reload is a fresh look at a list whose contents may have moved), `ByteSize`, `Keyboard` (whether the element under a key press owns it), `PlatformKeys` (⌘/⌥ or Ctrl/Alt, so a shortcut hint names a key the reader's keyboard has) |
| `views/` | One directory per feature: `shell/`, `servers/`, `entries/`, `search/`, `schema/`, `keys/`, `media/`, `plugins/`, `transfer/`, `settings/`. `shell/use-shell-shortcuts.ts` owns the two presses that belong to the shell rather than to a page — `?` for the shortcut list and `Ctrl`/`⌘` `,` for Settings — with `?` standing down while somebody is typing and the modified press not, since it types nothing. `entries/` keeps its naming rules in two pure files: `cell-format.ts` for one cell and `entry-labels.ts` for the heading column, which summarises a composite value rather than printing it (`String` on a list of components is `[object Object],[object Object]`) and prefers a property that can carry a name over whichever is declared first. Two more pure files sit beside them, neither needing a DOM to be tested: `column-widths.ts` (the table's `grid-template-columns`, the limits a drag is held to, and the `localStorage` round trip) and `entries-shortcuts.ts` (one lookup from a key press to what the page does with it). Their hooks are `use-column-widths.ts` and `use-entries-keyboard.ts` — the latter owns the row cursor and the single key listener that drives it — and `ColumnResizer` is the drag handle, which paints a resize straight onto the card's `--cols` and only commits to React state on release. `use-scroll-memory.ts` is what makes opening a row and coming back land where you left — recorded on every scroll, since no one exit from the list is the place to hang a save, and restored in a layout effect once the rows are there. `entries-page-request.ts` is the request behind one page — the `/search` route when there is text, the list route when there is not — split out because the query it takes is also what the store keys the answer by, and `use-entries-data.ts` is now that key plus `useResource` rather than the response-ticketing it needed before (D53). `use-route-guard.ts` beside them resolves the collection *index*, which is not a page: it forwards to the last collection opened in this scope (`CollectionVisits`), because the breadcrumb leads here from inside a collection and forwarding to the first one moved the reader somewhere they had not asked to go. `settings/rename/` (D51) is the one rename control, used by all three subjects — `use-rename-flow.ts` runs the two steps (a `?dry_run=true` request, then the real one), `RenameConfirmDialog` prints what the server said it will do, and the second of its two lists is what earns the dialog: claims whose reach changes although nothing rewrites them, which nothing else in the product would ever report. `settings/pages/` holds one file per settings page, with a data hook beside each; `ConfigurationPage` (D47) is the newest — one card and one Save per table of `silo.toml`, drawn from a spec the *server* sends so a new setting needs no admin change, with `config-section-draft.ts` as its pure half. `MediaStoragePage` (D45, D46) carries two cards with two Saves for the two tables behind it; `media-storage-draft.ts` and `media-policy-draft.ts` are their pure halves. The storage draft is seeded from what the *file* holds rather than from what is in force, which is what keeps a derived media path from being saved back as a literal; the policy draft deliberately does the opposite for the extension list, since an empty one is not a state the server accepts and a box showing nothing while something is enforced would lie in the other direction. `plugins/` (D40) holds the list, one plugin's page, and `PluginGrantPlan` — the pure half of the grant form, so the rules a grant screen must get right are testable without a DOM. Since D44 that page is a summary: `Plugin*Section` files are the contents of a `Sheet` (`components/modal/Sheet.tsx`, the app's second overlay — a modal asks a question, a sheet holds a section), opened from `PluginSectionButton`s that keep each section's *state* on the page. `claims/` beside it turns claim strings into words, with the claim *families* derived from its own catalogue rather than listed (D36). `plugins/panel/` (D41) is the iframe contract: `plugin-panel-protocol.ts` is the whole boundary and is pure so it can be tested without a DOM, `plugin-panel-preamble.ts` generates the `window.silo` client and theme tokens injected into a panel's `srcdoc`, and `PluginPanelFrame` is the parent half of the relay. `media/` (D48, extended by D49) holds the two-dialog delete flow: `media-delete-outcome.ts` is the pure half — splitting a bulk delete result's failures into `media_in_use` versus the rest (an empty `inUse` is Case A, no second dialog), and denormalizing `media_in_use` failures back against the assets a caller was showing — and `use-media-delete-flow.ts` is the hook that drives `DeleteAssetDialog`/`AssetInUseDialog` from it. Since D49 that hook's subject is a `DeleteSubject` union (a list of assets, or a folder path), so a single-file trash click, a multi-select and a recursive folder delete all share the one path rather than a second dialog pair existing for folders; `use-media-purge.ts` is `PurgeLibraryDialog`'s equivalent — its own purging/busy/error cells and confirm handler, split out of `MediaLibrary.tsx` on the same reasoning. That file reached 463 lines and is now the page and nothing else: `MediaDialogs.tsx` holds every overlay it can open (the flows passed whole, since each already owns a mutually exclusive pair and unpacking one would put that exclusivity back in the caller), `MediaContents.tsx` holds the empty states and both layouts (one component rather than a `MediaGrid` and a `MediaList`, which would be two identical prop lists to keep in step), `MediaPathTrail.tsx` the folder crumbs, and `MediaNotice.tsx` the one dismissible-message shape its three separate banner states share. `media-force-availability.ts` is the pure half of the force gate — whether `AssetInUseDialog`'s checkbox may arm, mirroring `RouteAuth.requireForcedMediaDelete` claim for claim, including its `visible_capped` check: `visible_count` is a true readable-referrer count since a D49 audit fix (it used to be `items.length`, a page size mislabeled as a count), so the capped case has to be checked on its own rather than falling out of `visible_count < usage_count` by construction. `use-media-library.ts` gives `not_found`/`invalid_id` and `media_delete_stalled` each their own dismissible banner state, neither cleared by the `reload()` a successful delete in the same batch triggers, and carries the D49 folder operations (`renameFolder`, `deleteFolderRecursive`, `purge`) on the same pattern; selection (which ids are checked, and the page-boundary rule that clears it) lives beside it in `use-media-selection.ts`, the subfolder counts in `use-folder-counts.ts` (derived from what is on screen rather than part of the library's own state, and one count-only request per *visible* subfolder, never the whole tree), and the message wording in `media-library-error.ts` — a class, so it does not sit inside a hook file against the one-artifact-per-file rule. What is left there is list state and the write operations over it. `FolderRow`/`FolderTile` are a clickable name/open region plus a separate actions cell (D49) — never a `<button>` wrapping the whole tile, since rename and delete are buttons of their own now and cannot nest inside one — and `RenameFolderDialog`/`MergeFolderDialog`/`PurgeLibraryDialog` are the three new dialogs, the latter two wrapping `components/modal/DangerConfirm.tsx` — `PurgeLibraryDialog` with the force opt-in inside it, `MergeFolderDialog` because a merge cannot be undone by renaming back. `use-media-rename-folder-flow.ts` drives that pair (a plain rename first, the merge offer only after a `409`) with `media-rename-outcome.ts` as its pure half, the same split `use-media-delete-flow.ts`/`media-delete-outcome.ts` already takes; `RenameFolderDialog` takes `busy` like every other dialog in the flow, added by a D49 audit fix — its `onSave` is async, and without it a double click sent two `PATCH`es. `MediaSelectionBar` is the bar a selection shows; `components/controls/Checkbox.tsx` is the plain selection checkbox it and the row/card checkboxes use, distinct from `forms/widgets/CheckboxWidget.tsx`'s RJSF `Toggle` |

## `packages/`

| Path | What it is |
|------|------------|
| `packages/shared/src/claims/` | The claim protocol: `Claims` is the facade over `ClaimVocabulary`, `ClaimGrammar`, `ClaimPresets`, `ClaimAuthorizer` and `ClaimSummary`. Both the server and the UI evaluate claims through it and nothing else. `claim-rewrite.ts` (D51) is what a rename does to a claim, and is pure so the one rule it turns on is testable without a store: a **literal** segment is a reference to an entity and is rewritten; a **wildcard** segment is a pattern over names and never is. `rename-permissions.ts` joins the four existing `*Permissions` classes, stating what a rename exercises so the admin can gate its controls on exactly what the routes enforce |
| `packages/shared/src/` (rest) | `errors/`, `hooks/`, `json/`, `keys/`, `media/`, `query/`, `schema/`. `json/` holds `MergePatch` (RFC 7396), which lives here because the server *applies* a config patch and the admin UI has to *produce* one — two implementations either side of one endpoint agree until a nested key is deleted. `hooks/` holds the `HookName` vocabulary, which moved here when hook delivery became a claim (D34) — the grammar validates it and the UI renders it, so neither side may own a second copy; D36 added the collection-level `collection.afterDelete` to it. Something belongs here when both sides need it *or* when shared itself must produce it; anything importing `bun:*`, node builtins, `hono` or React does not |
| `create-silo-plugin/src/` | The plugin scaffolder, published on its own. Nothing here may import from `apps/` or `packages/shared`, and nothing may use a `Bun.*` global — it runs under Node, and the facts it needs from silo are copied and drift-tested rather than imported. `render/` holds one class per generated file, and `plugin-routes.ts` holds the `--routes` grammar and the body ceiling it refuses against (D41) |

## `plugins/`

First-party plugins. Each is a workspace package that silo installs by copying,
so its directory is the unit that travels: no build step, no runtime dependency
on this repo, and `main` plus `contributes.ui.entry` are paths inside it.

There are two. Both are organised the way the server is — a directory per
subject, with a one-way dependency direction — and both carry `silo:api`
verbatim, which `first-party-plugin-drift.test.ts` holds them to.

`silo-plugin-strapi-import/` is the larger:

| Path | What it is |
|------|------------|
| `src/index.ts` | `activate`/`deactivate`, and the four route groups spread onto the one object `defineSiloPlugin` takes |
| `src/routes/` | One file per group — `SourceRoutes`, `UploadRoutes`, `PlanRoutes`, `ImportRoutes` — each answering with `static handlers()`, plus `RouteInput` for reading a body and refusing it as a 400 rather than a plugin fault |
| `src/worker/` | The state one worker holds. `ImportRuntime` is the single live instance the routes reach through (built in `activate`, because that is the only thing that runs before them); `PluginSettings` reads `[plugins.config]` and is the one place a default takes effect, since silo validates the table without filling a schema's `default` in |
| `src/strapi/` | Reading the export, and the whole of what silo needs to know about Strapi's storage layout. `StrapiDatabase` is the read-only handle and the content-type schema; `StrapiVersions` the draft/published rule the importer is correct or wrong by; `StrapiIdentifiers` the 55-character shake256 shortener that says what a long `collectionName` is actually stored as; `StrapiComponents` the table search that proves a candidate rather than guessing a plural; `StrapiFields` the content-manager configuration, the only place an export names a component's fields; `StrapiEnums` the declared `enumeration` values, confirmed against the column before they are carried, since Strapi enforces one on write and never on the rows already stored. `StrapiShape` describes one content type *and* its components — Strapi stores them the same way, so one description covers both — and `StrapiEntries` reads rows against it, breadth-first, with `StrapiMediaSlot` saying where a nested file's value belongs. `StrapiSchema` is the other direction — one list assembled into the nested JSON Schema its collection is created with |
| `src/staging/` | Where the `.db` and the supplied uploads live while a run needs them. Not under the data directory: D5 promises that is only the user's content |
| `src/silo/` | Writing into silo. `MediaLibrary` turns a Strapi file into `silo://media/<id>` and declares the configured folder once per run, `MultipartBody` encodes an upload by hand because `ctx.fetch` takes a value and not a `FormData`, `SiloNames` owns silo's id rule, `SiloTargets` reads the projects and environments a plan could point at |
| `src/panel/panel.html` | The admin panel, CSS and script inlined. One file because `contributes.ui` allows one: a directory would mean a static asset server inside the API (D41) |
| `src/types/silo-api.d.ts` | The `silo:api` declarations, verbatim from `apps/server/src/plugins/host/silo-api-types.d.ts` |
| `test/` | One file per subject, with `support/` holding the synthetic Strapi export, a temp directory helper and a fake `ctx` |

`silo-plugin-observability/` (D52) is deliberately the small one — it exists to
show that a first-party package holds no privilege a third-party package could
not ask for. The measuring is silo's; the plugin only draws it:

| Path | What it is |
|------|------------|
| `src/index.ts` | One route group spread onto the object `defineSiloPlugin` takes. No `activate`: it holds no state |
| `src/routes/snapshot-routes.ts` | The whole plugin. `GET /snapshot` calls `/api/observability` through `ctx.fetch` and passes the status and body back, so the panel reaches the core endpoint through the plugin's own grant rather than a private channel |
| `src/panel/panel.html` | The dashboard, CSS and script inlined, dependency-free — KPIs, the sixty-minute traffic chart, the latency distribution, the endpoint table, the status-mix bars and the storage cards. Every node is built with `textContent`, never `innerHTML`. The charts are pointer-driven: one shared tooltip, positioned `fixed` so it cannot grow `body.scrollHeight` and feed back into the frame height the admin derives from it, and the traffic chart re-fits its `viewBox` to its rendered box so it fills the panel instead of letterboxing. Each panel carries an `i` explaining its own numbers |
| `src/types/silo-api.d.ts` | The `silo:api` declarations, verbatim from `apps/server/src/plugins/host/silo-api-types.d.ts` |
| `test/` | The manifest, the route's pass-through of a refusal, and the panel's dependency-free/empty-state guarantees |
