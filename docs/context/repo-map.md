# Repo map

> Where everything lives. The rules that shape it are in
> [code-design.md](code-design.md).

## The workspace

```
silo/
├─ apps/
│  ├─ server/                 @silo/server — the CLI, HTTP API, core and adapters
│  └─ admin/                  @silo/admin  — the React admin UI
├─ packages/
│  ├─ shared/                 @silo/shared — runtime-neutral logic both sides need
│  ├─ create-silo-plugin/     the published plugin scaffolder
│  ├─ silo-client/            @org-quicko/silo-client — the published TypeScript API client (D61, D71)
│  ├─ silo-client-java/       in.org.quicko.silo:client — the published Java API client (D69)
│  └─ silo-client-dart/       silo_client — the published Dart API client (D91)
├─ plugins/                   first-party plugins, one workspace package each
│  └─ silo-plugin-strapi-import/  a Strapi 5 SQLite import — entries and media — with its own admin panel (D41)
│     ├─ src/                     index.ts, then routes/ worker/ strapi/ staging/ silo/ panel/ types/
│     └─ test/                    one file per subject, with support/ holding the synthetic export
├─ tools/                     build, packaging, seeding and version tooling
├─ packaging/                 Homebrew formula template and RPM inputs
└─ docs/                      context/ (what is), design/ (why), guide/ (how to use it)
   └─ openapi.json            the HTTP API as OpenAPI 3.1, hand-written and kept in step by hand
```

One Bun workspace, one install root, one `bun.lock`. The root `package.json`
holds no runtime dependencies — it declares the members and delegates every
script.

## Root files

| Path | What it is |
|------|------------|
| `package.json` | Workspace root. Its `version` is the single source of truth (D28) — the binary, the archives, the RPM and the Homebrew formula all derive from it, and the release workflow refuses a tag that disagrees |
| `tsconfig.base.json` | Compiler options shared by every Bun-side package |
| `tsconfig.json` | One typecheck pass over the server, `shared` and `tools` |
| `CONTEXT.md` | Current state, and the index into `docs/context/` |
| `IMPLEMENTATION.md` | Vision, the decisions log, and the index into `docs/design/` |
| `CLAUDE.md` | Standing instructions for AI assistants |
| `silo.toml` | A commented example config; every key is optional |
| `Dockerfile` | Two stages — build `@org-quicko/silo-client` then the admin UI, then a runtime image with only the server's dependencies. Each stage copies the manifests of the workspaces it installs and of those they depend on, and no others: Bun skips a `bun.lock` workspace missing from the context, but aborts when a present one depends on it. The runtime stage runs the server *from source*, where no `--define` can reach `SiloVersion`, so a `SILO_VERSION` build arg is baked into the image's `ENV`: the release passes the version it is cutting, nothing else passes anything, and an image built on a laptop goes on saying `-dev` (D90) |
| `.gitattributes` | `* text=auto eol=lf`. What it fixes is the *working tree* on Windows, where `core.autocrlf=true` would otherwise check the repo out as CRLF and break the byte-for-byte drift test between the scaffolder's `silo-api.d.ts` and the host's copy |

## `apps/server/src/`

| Directory | What it holds |
|-----------|---------------|
| `cli/` | `Cli` parses argv, `CliOptions` owns the flag table, `UsageText` the help, `CommandRouter` routes in three tiers, and `commands/` is one class per subcommand. The config file itself is chosen by `CliOptions.configPath`: `--config`, then `SILO_CONFIG`, then `silo.toml` beside the process (D50). `runtime/silo-runtime.ts` does the dependency wiring. `commands/mcp-command.ts` (D86) is the one subcommand that is a client: it runs in the first tier with `init`, reads no config and opens no storage, and hands `--url`/`--key` (else `SILO_URL`/`SILO_API_KEY`) to `McpStdioBridge` |
| `config/` | `Config` and its sub-shapes — including `storage-config.ts`/`storage-defaults.ts`, whose Postgres keys (D94) only that driver reads — including D72's `http-config.ts`/`http-defaults.ts`, the listener's own settings, where `idleTimeout` is clamped to the runtime's ceiling rather than refused, and D85's `transfer-config.ts`/`transfer-defaults.ts`, what a streamed archive may weigh and expand to — `ConfigLoader`, `ConfigScaffold` (the annotated default file, written by `silo init` and by an install that has no file to list a plugin in), and the two editors of a live `silo.toml`: `PluginBlockWriter`, which appends and removes a `[[plugins]]` entry rather than re-serialising, and `BlobStorageTable` (D45), which reads and replaces the `[blob_storage]` table. Both edit text and parse the result before writing it, refusing any edit that would have changed anything else |
| `core/domain/` | `Entry`, `Scope`, `Collection`, `Meta` and their helpers, plus D51's three record shapes — `project-record.ts`, `environment-record.ts`, `collection-record.ts` — and `system-collections.ts`, which names silo's own eight collections once so both adapters seed the same set. `SystemCollections.isKnown` is deliberately **not** the same question as `EntryUtils.isSystemCollection`: the latter asks whether a name is `_`-prefixed and reserves the whole namespace, and stays the security boundary. `portable-data.ts` (D92) is the rule every adapter shares for what entry data may hold: no NUL character and no unpaired surrogate, in keys or values |
| `core/ports/` | `Storage`, `BlobStorage`, `DerivedIndex` — interfaces only, importing no adapter. `IndexedStorage` (D92) is the optional capability a store implements when it keeps a search index inside its own writes; the runtime asks the store for it rather than naming an adapter class. `OwnedStorage` and `MeasuredStorage` (D94, with `storage-measurement.ts`) are the same kind: a store that guards its own single owner, which `serve` claims, and one that reports on itself for `GET /api/observability` |
| `core/services/` | The application service layer. `SiloService` is the facade; `scopes`, `collections`, `entries`, `search`, `keys`, `plugins`, `audit`, `transfer`, `media` and `renames` are the services behind it. `rename-service.ts` (D51) owns the *order* a rename happens in — refuse, plan the claim cascade, check the `silo.toml` half, rename the record, cascade, restart any plugin whose grant moved, audit — as one service rather than a method on each of the three, since that order is the hard part and is the same every time. `support/scope-rename-cascade.ts` is the claim rewrite it drives, staged behind a `_scope_renames` marker that doubles as a name reservation. `variable-service.ts` (D57) is the eleventh: declaring is cut from valuing along the line the routes enforce, and `forPayload` is where the cheap path lives — a response referencing nothing reads nothing. `support/` holds what they share — the `ServiceContext`, the schema cache, the write lock, and `variable-store.ts`, the `_variables` accessor that keeps `Scope.System` and the collection name in one place the way `MediaCatalogStore` does. `media/` holds **two** staged sagas, both because the operation spans more than one adapter write and no `Storage` method can make it atomic: `media-deletion-service.ts` stages `state: "deleting"` on one record (D23), and `media-folder-move-service.ts` stages a `_media_folder_moves` marker naming `from` and `to` (D49). Both are replayed at startup from `serve-command.ts`, and both count failures rather than throwing, so neither can stop the server booting. `MediaAssetService.replaceContent` (D67) deliberately joins neither: it writes the same blob key and then the same record, so the one write that matters is the record's and there is nothing partial for a marker to describe |
| `core/errors/`, `core/query/`, `core/schema/`, `core/keys/`, `core/media/`, `core/search/`, `core/transfer/`, `core/hooks/`, `core/plugins/`, `core/audit/`, `core/variables/` | One subject each. `core/query/codepoint-order.ts` (D92) is the one string order every adapter answers in, for comparisons, sorts and listings, and `entry-nodes.ts` is the in-memory selection and total sort order that the fs adapter and `ScanSearcher` both read. `core/media/media-disposition.ts` (D83) decides which content types leave `/media/{id}` inline and which as an attachment, and `media-paths.ts` owns the blob key policy in one function — `media/<id>` since D88, which is the request path, so a bucket holding the object can answer that URL itself; `media-rekey-result.ts` is what `services/media/media-rekeyer.ts` reports after moving assets still on the older `<id><ext>` key. `core/variables/` is D57's: `variable-record.ts` is the stored shape (one document per declaration, `values` keyed by environment record id), `variable-refs.ts` the walker that decides whether a response needs any lookup at all, `variable-values.ts` the synchronous per-scope answer a response resolves through — `MediaLinks`' counterpart, and sharing its three-state distinction between undeclared, declared-and-unset, and set — and `variable-resolver.ts` the walk that substitutes, which runs *after* `MediaResolver` and is deliberately not schema-driven. `core/plugins/` is the grant record and its rules (D34) — the store-side half of plugin authority, including the config override a running instance may be given (D39), which `plugins/` reads but does not own. `core/audit/` is the authority-change trail (D38): the event shape, the actor, and the closed list of actions. `core/schema/` is the validator and everything that prepares a document for it: `SchemaValidator` (Ajv 2020, one compiled validator per scope+collection), `SchemaBundler`, `SchemaRefRewrite`, `RemoteSchemaLoader`, and `SchemaChangeGuard` — D70's rule that a collection's constraints are frozen while it holds entries, reached by both writers of a stored schema (`CollectionService.putSchema` and `Importer`) so neither can be the one that forgets. `core/transfer/` is one walk and two destinations since D73: `Exporter.export` writes through an `ExportSink` (`sink/directory-export-sink.ts` for `--dir`, `sink/tar-export-sink.ts` over `tar/tar-writer.ts` for the stream), so the tarball is produced as it is read rather than staged in a temp tree first — which is what made time-to-first-byte the length of the whole export and got the response closed under it. `tar/` is silo's own ustar writer, `tar-header.ts` being the 512-byte block and the PAX record a path past 100 bytes needs; reading is still `tar.x`, so only the writing side is ours. The walk is split by subject: `export-walk.ts` (projects, scopes, schemas, entries, and the media references it collects on the way), `export-system.ts` (`_system`, whose media and variable filters need what that walk found, which is why it runs after it), `export-media.ts` (the bytes) and `export-entry-file.ts`/`export-marker.ts` for the two file shapes both halves write. `transfer-selection.ts` is the one parser and matcher for D74's `project[/env[/collection]]` rules and `media-mode.ts` the three modes; `import-filter.ts` narrows a walked archive to them and `import-authority.ts` answers the question replace mode has to ask before it empties anything. `import-entries.ts` is what a walked collection's entries arrive as since D77 — a directory recorded rather than read, opened one file at a time when the importer gets there — and `tar/gzip-stream.ts` is D76's paced gzip, which exists because the web `CompressionStream` has no backpressure and held the whole archive — which is the fix for a partial archive wiping a destination's media library. `Importer` takes a path, a `Buffer` or a stream, and since D85 splits a streamed load into `stage` — spool, then unpack through `archive-extractor.ts`, an `Unpack` driven by hand so the disk budget in `import-limits.ts` can abort it from tar's own headers before an entry is written — and `importDir`, so `TransferService` holds the write lock around the second alone; a truncated upload still fails with the gzip error rather than a missing `manifest.json`, and the staging tree sits under `<data>/transfer/` rather than the platform temp directory, which on a hardened unit is RAM. `import-grants.ts` and `import-system-gate.ts` (D84) are what of `_system` a caller may load, asked after the filter and before a write. In replace mode the importer writes the archive's rows over what is there and `prune`s the rest, never emptying first |
| `adapters/storage/sqlite/` | The indexed adapter, split per table: migrations, meta, scopes, **collections** (`sqlite-collection-store.ts`, which replaced `sqlite-schema-store.ts` when `collections` replaced the `schemas` table — D51), entries, media references, FTS documents, and the compiler and searcher on top. `sqlite-scope-resolver.ts` is the one place names meet ids, forwards only and cached whole; `sqlite-record-mapper.ts` maps the three record tables' rows; `sqlite-id-claim.ts` holds the rule for an id an importer supplied; `sqlite-connection.ts` is the handle every one of them holds instead of the raw `Database`, owning an unbounded cache of the statements prepared against it so that `close()` can finalize them all and actually release the file. `sqlite-read-worker.ts` (D81) is a store's handle on `sqlite-read-thread.ts`, the one `Worker` per process — one connection per database path, source shipped as a `data:` URL like the plugin host's, `query_only`, held while a read is out and unref'd when idle — that `SqliteEntryStore.list` and `SqliteSearcher.search` run their scans on, with a per-store queue that sheds as `503 busy` |
| `adapters/storage/fs/` | The plain-files adapter, split the same way, with `FsLayout` holding the on-disk path grammar that *is* the export format (D5) — still keyed by **name**, because the tree is meant to be read by a human, with the record ids in the markers `fs-marker.ts` reads and writes. `fs-collection-store.ts` replaced `fs-schema-store.ts` and owns the one rename that is not a single syscall: the destination marker carries `moving_from` and `resumePending` finishes the move at the next open (D51). `fs-system-seed.ts` is `SqliteMigrations.seedSystemRecords`' counterpart, so both adapters answer `listCollections(Scope.System)` alike. There is deliberately **no** name-to-id cache here, where SQLite has one |
| `adapters/storage/postgres/` | The Postgres adapter (D93), split per table like SQLite's. `pg-connection.ts` is the pool and the only file that imports `Bun.SQL` (`prepare: false`, every error through `pg-error-map.ts`, which maps SQLSTATEs to 409/404/400/503). `pg-tables.ts` holds the schema-qualified table names and the schema-name grammar; `pg-migrations.ts` the version check, the DDL under an advisory lock, the stricter format guard and the seeding. `pg-compiler.ts` turns the query AST into jsonb SQL with `pg-params.ts` numbering the parameters. `pg-scope-resolver.ts` is SQLite's name cache plus a generation guard, since its lookups await. `pg-owner-lock.ts` is the per-schema session advisory lock on a connection outside the pool (D25). Since D94 `pg-connection.ts` also retries what cannot have committed and drains on close, `pg-unavailable-error.ts` is the 503 that says why, `pg-scan-gate.ts` keeps two connections free for writes, `pg-startup.ts` waits for a server that is not up yet, and the owner lock has a heartbeat (`pg-ownership-taken-error.ts` for a rival). Since D95 search is `pg-searcher.ts`, over `entry_search`: `pg-search-index.ts` holds its table, index and stamp, `pg-search-document.ts` builds the stored `tsvector` or folded text, `pg-search-text.ts` the query side, `pg-search-document-store.ts` the write inside `put`. Selected by `[storage] driver = "postgres"` |
| `adapters/blob/` | Filesystem and S3 blob stores. `s3-public-url.ts` (D58) is the one artifact that knows how a bucket's objects are addressed publicly — four forms, decided by `endpoint` and `force_path_style` — which `S3BlobStorage.publicRoot()` answers with and `MediaLinks` builds every media URL from. `FsBlobStorage.put` writes a temp sibling and renames over the key (D67), so a key never holds a partial object once replace makes overwriting an existing one ordinary — S3 `PUT` always behaved that way. Since D80 the port has an optional seventh, `stream(key, range?)`: `FsBlobStorage` answers it with `file-byte-stream.ts`, a pull-based 64 KB reader over a file handle — hand-written because every runtime file body was measured to buffer or mis-slice — and `S3BlobStorage` with the object handle's stream, a slice of which is a ranged `GetObject` |
| `adapters/http/` | The outbound client used by server-to-server copy. `exportArchiveStream` hands the source's archive back as a stream, peeking its first chunk to keep the empty-archive check and putting that chunk back — the destination would otherwise buffer whole what the source just streamed |
| `http/` | `SiloServer` builds the Hono app; `response-sandbox.ts` (D83) is the pair of headers, `nosniff` and a `Content-Security-Policy`, that `MediaRoutes` and `ExtRoutes` put on every byte silo did not write; `routes/` is one class per route group — `VariablesRoutes` (D57) registers before `ProjectsRoutes` so `variables` is never read as an environment name, and splits its paths by *reach* rather than by page: declarations under the project, values under the environment — `MediaStorageRoutes` (D45) and `MediaFolderRoutes` (D49, `/api/media/folders`'s list/create/rename-move/delete-recursive) both register before `MediaRoutes` so `storage` and `folders` are never read as an asset id; `MediaDeleteBatch` and `MediaInUseDetails` are the per-id outcome loop and the claim-filtered "still in use" facts, factored out of `MediaRoutes` because bulk delete, recursive folder delete and purge all need the same two things (D49) — including `ExtRoutes`, the single handler every plugin route is matched and dispatched through (D36) — `auth/` the claim helpers, including `RouteAuth.requireMediaContentAuthority` (D49, extended by D67), the one `async` because the reach of a force-delete or a replace is data-derived rather than read off the route, and the injected-principal slot a plugin dispatch arrives in (D35), `middleware/` logging, auth and body ceilings — `BodyLimitMiddleware` (D79) refuses an oversize body from its headers before auth, at `[http] max_json_body_size_mb` for every route that takes a document and not at all for the four upload routes and plugin routes, which the listener's own cap bounds — where `LoggingMiddleware` since D52 also records one bounded metric per `/api/` request, on the same timer as the access log but switched independently of it, and `ObservabilityRoutes` is the one route that reads them back. `TransferRoutes` returns `/api/export` as a stream rather than a body it has read, which is why it holds no temp file of its own, and takes `/api/import`'s body as one; its multipart branch stays for callers posting a form, but only the raw branch truly streams, since a part cannot be found without parsing the body around it |
| `mcp/` | The Model Context Protocol surface (D86). `McpRoutes` registers `POST /api/mcp` and the `405` on `GET`/`DELETE`; `McpServer` answers `initialize`, `ping`, `tools/list` and `tools/call` one JSON-RPC message at a time; `McpToolCatalog` is the ordered tool set and `tools/` its five hand-written groups (`InstanceTools`, `CollectionTools`, `EntryTools`, `SearchTools`, `MediaTools`) over the shared `ToolSchemas` and `ToolPaths` fragments; `McpArgumentValidator` checks arguments with AJV; `McpToolRunner` dispatches a call through the same Hono app with the caller's credential and `McpToolResponse` shapes the route's answer into a result; `McpStdioBridge` is what `silo mcp` runs. `json-rpc.ts` and `mcp-protocol.ts` are the protocol vocabulary. Import from `mcp`, never a file inside it |
| `logging/` | `Logger`, the level union, the `LogSink` port and its console/file implementations, and the two read-side helpers. Nothing here knows about HTTP or storage |
| `observability/` | The process-local metrics accumulator behind `GET /api/observability` (D52). `Observability` is the facade the server holds one of; `RequestMetrics` owns the process-lifetime counters, the per-endpoint table and the rolling sixty-minute chart, `LatencyHistogram` the fixed-boundary distribution beneath both, and `StorageMetrics` the cached background directory and filesystem probes. Everything here is **bounded on purpose** and the bounds are the design: series keys are Hono's registered route pattern so no id or query becomes a series, endpoints collapse into one `* <other>` row past 256, the chart prunes to sixty minutes, a percentile is a bucket bound clamped to the observed maximum, and a directory walk skips the media subtree, follows no symlink and stops at 50,000 entries. Nothing here reads content, a caller or a path. Import from `observability`, never a file inside |
| `plugins/` | Six submodules with an index each — `manifest/` reads what a plugin declares without running it: since D36 that is a `contributes` block (hooks, routes, a `runtime`, providers — none of them exclusive) and a `permissions` block splitting `required` from `optional` with a reason for each, read by one small reader per block so no file owns two grammars — `contract/` describes the client a plugin is handed and emits both halves of it (D35), `host/` executes it, `runtime/` is what it can see and do, plus the `PluginApiDispatcher` its `ctx.fetch` lands in and the `PluginRouteTable` a request is matched against (D36), `registry/` is the single wiring site and, since D39, the live one — `PluginRegistry` is a mutable ordered set that only `PluginSupervisor` mutates, with `PluginLifecycle`, `PluginConfigurator`, `PluginRescan`, D42's `PluginInstallation`, D43's `PluginUninstallation` and the read-only `PluginInspector` beside it — and `install/` acquires it. `PluginInstallation` and `PluginUninstallation` are the two places that *write* `silo.toml`: the first holds the order an install happens in (refuse before fetching, refuse before running, spawn ungranted, grant, list last) and the rule that the block it appends carries `claims = []`, because only the record half of a grant is checked and revocable; the second holds that order reversed (un-list first and fail hard, stop, forget the record and its key, delete the files last and forgive it), because a block naming a package that is gone fails the whole process rather than that plugin. `manifest/` also owns D41's two additions — a route's declared `body` contract, and `contributes.ui`, whose panel `registry/plugin-panel.ts` reads off disk for the one route that serves it. Import from `plugins`, never a file inside |
| `settings/` | Settings an operator changes through the API rather than by editing a file (D45, D46). Two subjects, one shape, which is what the directory is named for: a pure half that decides which value wins, and a supervisor that writes one table of `silo.toml` and applies the result live. `MediaStorageSettings`/`MediaStorageSupervisor` own `[blob_storage]` — parse a body, merge over *the file* so an env-held secret is never copied into it, check the driver, write, re-read the config the way a start reads it, open the store from that, swap it in, and put the file back if any of it fails. `MediaPolicySettings`/`MediaPolicySupervisor` own `[media]` the same way: where media URLs point and what the library accepts. Separate because a bucket that will not open must not hold up a correction to the allowlist. `ConfigSectionSettings`/`ConfigSupervisor` (D47) cover the rest of the file, driven by the `ConfigSections` spec rather than hand-written, and are the first pair that cannot always apply what they save: they keep the config the process *started on* separate from the file and report the difference as a restart owed. `ConfigFileAccess` (D50) is what all three ask before reporting a form writable, and what wraps every write: it probes the path rather than the fact of having been given one, and turns a filesystem refusal into a `400` naming the path instead of a `500` naming nothing. `ConfigSecrets` (D94) masks a `secret` field — `[storage] url` — on the way out, so a password never reaches an admin session. Import from `settings`, never a file inside |
| `runtime/` | Process lifecycle: the run file that records a live server — since D82 judged live by identity (`RunFile.liveness`: not this pid, same boot, pid present, refreshed within `StaleAfterMs`) and refreshed by `serve` every `HeartbeatMs`, written through a temp sibling and a rename — `boot-id.ts` reading the kernel's boot id where there is one, the daemon mechanics, the listen-address grammar, and the process title |

## `apps/admin/src/`

| Directory | What it holds |
|-----------|---------------|
| `api/` | `SiloApi` is the facade; `clients/` is one class per resource, `transport/` holds the one place a request is made, `types/` the DTOs. `EntriesApi` and `SearchApi` append `?variables=raw` to **every** read (D57): the admin is an editor, and a form seeded with a resolved value saves that value back over the reference somebody typed |
| `claims/` | `ClaimGroups` (a claim set → the handful of sentences it means) and `ClaimWords` (the vocabulary it reads them in). Used by the key form and the plugin grant screen, which is why it is not inside either |
| `components/` | Shared visual primitives, grouped by kind: `modal/`, `buttons/`, `feedback/`, `data/`, `brand/`, `controls/`, `navigation/`, `browser/`. `browser/` is the column browser — `BrowserColumns` (the row of panes), `BrowserColumn` (one pane's header, count, search slot and list), `ColumnItem` (one row, with an optional `lead` for a checkbox and `action` for a hover control) and `ColumnPlaceholder` — lifted out of `views/servers/` when the Data Transfer scope picker needed the same thing (D74). It is one module rather than two copies for the reason the rest of this directory exists: a row style that lives in two places is a row style the two screens will stop sharing. `ServerManager.module.css` keeps only its own chrome and a second copy of the `columnReveal` keyframes, since a CSS module scopes keyframe names too. `modal/` is `Modal` plus the pieces a dialog is assembled from — `ModalHeader`, `ModalIcon`, `ModalCopy`, `ModalBody`, `ModalSubject`, `ModalActions`, and `ModalError`, the one line a dialog says its *own* failure in (D66 follow-up): a reader looking at a dialog is not looking at the page banner behind it, so a refusal that lands there reads as nothing happening. `DangerConfirm` uses it in place of the local error span it carried. `buttons/` carries two copy affordances rather than one: `CopyButton` is the labelled button a snippet or a one-time secret is taken with, `CopyIconButton` its 20px icon-only twin for a value stated inline — an entry's id in the form's rail — where a labelled button would outweigh the fact it sits beside. `feedback/` holds the app's one waiting state (D53): `Spinner` is the ring — the theme's own `--line-2` track and `--accent` arc, with `prefers-reduced-motion` answered in the one place — and `LoadingState` pairs it with the sentence naming what is being waited for, `fill` centring in the viewport for a state that *is* the screen. `ErrorBoundary` is the other end of that pair and the app's last line: `main.tsx` wraps the whole tree in it, so a render error shows what threw and offers *Try again* (a remount by key) before *Reload*, rather than leaving a white document with nothing to act on — the state the schema editor's Code tab put the admin in when two copies of `@codemirror/state` reached one bundle |
| `views/ai-assistants/` | Current-connection MCP setup. `AiAssistantConfig` names every client's connection `silo` and creates escaped command/config fragments and Cursor’s direct URI; `AiAssistantsPage` presents the four client actions without creating another key or claiming that an external client has connected. `DesktopExtension` builds the downloadable Claude Desktop bundle, whose server URL and API key are editable settings; `DesktopBridgeSource` is the Node entry point inside it. |
| `forms/` | The RJSF theme — `templates/`, `widgets/`, `fields/` — plus the two pure files that decide what it draws. `variables/` (D57) is the `{{NAME}}` affordance every string field is wrapped in: `variable-hints.ts` is its pure half (which state a reference is in, what the caret is part-way through typing, what a completion inserts), `VariableTextField.tsx` is the editable surface — a `contenteditable` rather than an `<input>`, because a chip carrying the name *and* the value is wider than the `{{NAME}}` it stands for and so has to be a real element in a real flow — `variable-dom.ts` is the boundary that keeps the string the source of truth and the DOM a rendering of it (a chip reads back as `{{NAME}}` whatever it displays, plus the caret arithmetic a mid-typing re-chip needs), `VariableAffordance.tsx` puts the completion list and the hover popover around that field, and `variable-form-context.ts` is how the block reaches a widget: on RJSF's `formContext`, where `url` and `apiKey` already travel, because a React provider outside RJSF's tree is not visible inside it. `build-ui-schema.ts` picks widgets, reading types through `SchemaType` and descending into an array's `items` as well as an object's `properties`: every imported property is `["object", "null"]`, so a comparison against `'object'` stopped the walk at the first nested component and the ## `plugins/`

First-party plugins. Each is a workspace package that silo installs by copying,
so its directory is the unit that travels: no build step, no runtime dependency
on this repo, and `main` plus `contributes.ui.entry` are paths inside it.

There are two. Both are organised the way the server is — a directory per
subject, with a one-way dependency direction — and both carry `silo:api`
verbatim, which `first-party-plugin-drift.test.ts` holds them to.

`silo-plugin-strapi-import/` is the larger:

| Path | What it is |
|------|------------|
| `src/index.ts` | `activate`/`deactivate`, and the four route groups spread onto the one object `defineSiloPlugin` takes |
| `src/routes/` | One file per group — `SourceRoutes`, `UploadRoutes`, `PlanRoutes`, `ImportRoutes` — each answering with `static handlers()`, plus `RouteInput` for reading a body and refusing it as a 400 rather than a plugin fault |
| `src/worker/` | The state one worker holds. `ImportRuntime` is the single live instance the routes reach through (built in `activate`, because that is the only thing that runs before them), and it holds the settings, the sessions and the janitor rather than an import; `ImportSession` is one operator's staged database, uploads, inventory and jobs, and `ImportSessions` keys those by `request.caller.id`, gives each a directory under `work_dir/sessions/`, adopts what a restart left there and sweeps a session idle past `session_ttl_hours`; `PluginSettings` reads `[plugins.config]` and is the one place a default takes effect, since silo validates the table without filling a schema's `default` in |
| `src/import/` | The plan and the run. `ImportPlans` proposes one step per list and validates what the panel hands back — the scope, the media folder and layout — with `ImportSteps` reading one step on its own (its list, its mode, whether it may be flattened); `ImportJob` runs a validated plan off the request that started it, one step at a time, `ImportJobs` keeps one session's runs with one in flight at a time, and `RunningTargets` is the bound across sessions — every `project/env/collection` a run writes, claimed while it runs, so two operators import at once and never into the same collection |
| `src/strapi/` | Reading the export, and the whole of what silo needs to know about Strapi's storage layout. `StrapiDatabase` is the read-only handle and the content-type schema; `StrapiVersions` the draft/published rule the importer is correct or wrong by; `StrapiIdentifiers` the 55-character shake256 shortener that says what a long `collectionName` is actually stored as, plus the camelCase → snake_case column spelling; `StrapiComponents` the table search that proves a candidate rather than guessing a plural, falling back to a match on the component's *fields* for the renamed category whose uid and table share no word; `StrapiFields` the content-manager configuration, the only place an export names a component's fields, and what that fallback is proved against; `StrapiEnums` the declared `enumeration` values, confirmed against the column before they are carried, since Strapi enforces one on write and never on the rows already stored. `StrapiShape` describes one content type *and* its components — Strapi stores them the same way, so one description covers both — and `StrapiEntries` reads rows against it, breadth-first, with `StrapiMediaSlot` saying where a nested file's value belongs. `StrapiSchema` is the other direction — one list assembled into the nested JSON Schema its collection is created with. `StrapiShapes.isEmpty` is what decides a content type is not worth offering — a component field no table was proved for writes `[]` and can write nothing else, so a content type made only of those is reported under `StrapiInventory.skipped`, with the reason naming the component, rather than importing as one empty entry per document. `StrapiFlattenings` decides whether a single type is nothing but a wrapper around one repeatable component, so it can be imported one entry per item instead; `StrapiMediaOwners` reads which collections of a run reference each upload, for the `by-collection` media layout |
| `src/staging/` | Where the `.db` and the supplied uploads live while a run needs them, rooted at the session's own directory so one operator's sweep cannot reach another's files. Not under the data directory: D5 promises that is only the user's content |
| `src/silo/` | Writing into silo. `MediaLibrary` turns a Strapi file into `silo://media/<id>` and declares each folder it lands in once per run, `MediaFolders` decides which folder that is under the configured layout — one for everything, or one per collection plus `shared` — `MultipartBody` encodes an upload by hand because `ctx.fetch` takes a value and not a `FormData`, `SiloNames` owns silo's id rule, `SiloTargets` reads the projects and environments a plan could point at |
| `src/panel/panel.html` | The admin panel, CSS and script inlined. One file because `contributes.ui` allows one: a directory would mean a static asset server inside the API (D41) |
| `src/types/silo-api.d.ts` | The `silo:api` declarations, verbatim from `apps/server/src/plugins/host/silo-api-types.d.ts` |
| `test/` | One file per subject, with `support/` holding the synthetic Strapi export, a temp directory helper and a fake `ctx` |

`silo-plugin-observability/` (D52) is deliberately the small one — it exists to
show that a first-party package holds no privilege a third-party package could
not ask for. The measuring is silo's; the plugin only draws it:

| Path | What it is |
|------|------------|
| `src/index.ts` | One route group spread onto the object `defineSiloPlugin` takes. No `activate`: it holds no state |
| `src/routes/snapshot-routes.ts` | The whole plugin. `GET /snapshot` calls `/api/observability` through `ctx.fetch` and passes the status and body back, so the panel reaches the core endpoint through the plugin's own grant rather than a private channel |
| `src/panel/panel.html` | The dashboard, CSS and script inlined, dependency-free — KPIs, the sixty-minute traffic chart, the latency distribution, the endpoint table, the status-mix bars and the storage cards. Every node is built with `textContent`, never `innerHTML`. The charts are pointer-driven: one shared tooltip, positioned `fixed` so it cannot grow `body.scrollHeight` and feed back into the frame height the admin derives from it, and the traffic chart re-fits its `viewBox` to its rendered box so it fills the panel instead of letterboxing. Each panel carries an `i` explaining its own numbers |
| `src/types/silo-api.d.ts` | The `silo:api` declarations, verbatim from `apps/server/src/plugins/host/silo-api-types.d.ts` |
| `test/` | The manifest, the route's pass-through of a refusal, and the panel's dependency-free/empty-state guarantees |

## `.github/`

Two releases, cut apart on purpose: one ships a binary an operator installs,
the other a library on somebody else's dependency graph. They share no tag, no
version and no job. A third workflow is the alpha lane, where a `v*-alpha*` tag
publishes a container image and nothing else. Beside them, the forms a stranger
fills in before either release is anybody's problem.

| Path | What it is |
|------|------------|
| `workflows/release.yml` | silo itself, on a `vMAJOR.MINOR.PATCH` tag and nothing else — a `-rc.1`, `-beta` or `-SNAPSHOT` tag starts no run, and a dispatch refuses such a version: one executable per platform, checksummed, signed by cosign and GPG, published as a GitHub release, then the Homebrew tap, the dnf repo index and the container image. It refuses a tag that disagrees with the root `package.json` (D28), and builds the client before `bun test`, since the admin suites import it. The image is built once per architecture on a native runner, stamped with the version it is cutting, smoke-tested there and pushed by digest to Docker Hub and GHCR at once; `publish-image` names the two digests `:VERSION` and `:latest` in both registries, signs each index with cosign and attests its provenance, and waits for the GitHub release before any of it (D90). `workflow_dispatch` builds and uploads to the run without publishing, image included. Needs `DOCKERHUB_TOKEN` and the `DOCKERHUB_USERNAME` variable, both organisation-wide |
| `workflows/release-docker-snapshot.yml` | The alpha lane, on a `v*-alpha*` tag — which `release.yml`'s filter cannot catch, so an alpha builds no executables, cuts no GitHub release and reaches no tap. It type-checks, tests, and pushes one amd64 image to `ghcr.io/org-quicko/silo:<version>` and `:alpha`, never `:latest` and never Docker Hub, since `latest` in that registry is now a real release (D90). `workflow_dispatch` runs the checks and pushes nothing |
| `workflows/release-silo-client.yml` | `packages/silo-client` to npm, on a `silo-client-v*` tag — which `release.yml`'s filter cannot catch, so a client release builds no binaries and touches no tap. The version gate reads the *package's* manifest, a pre-release goes out under the `next` dist-tag, and the gate before publishing is the package's own `test:packaged` over the packed tarball. `workflow_dispatch` runs the same checks and `npm publish --dry-run`. Needs one secret, `NPM_TOKEN` |
| `ISSUE_TEMPLATE/bug_report.yml` | The bug form. Required: two preflight checks, what happened, what was expected, steps, area, version, install method, platform. Optional: storage driver, logs (`render: shell`), `silo.toml` with secrets removed (`render: toml`), anything else. Labels the issue `bug` |
| `ISSUE_TEMPLATE/feature_request.yml` | The feature form: problem before solution, what was tried instead, area, and a willing-to-PR box. Labels the issue `enhancement` |
| `ISSUE_TEMPLATE/config.yml` | Blank issues stay **on**, because Discussions are off and a question would otherwise have nowhere to go. Two contact links: private security advisories, and `docs/guide/` |

The `Area` dropdown is the same list in both forms, and it is a list of this
map's own directories as a reader of the README would name them. Keep the two
copies identical: GitHub has no include, and a form that offers areas the other
does not is how a bug and its fix end up filed against different parts of silo.

## `docs/`

Three audiences, three directories, and nothing states the same fact twice.

| Path | What it is |
|------|------------|
| `context/` | What exists *now*, for whoever is about to change it — this map, `architecture.md`, `code-design.md` and `changelog.md`. Indexed by `CONTEXT.md` |
| `design/` | *Why* it is shaped this way, one file per spec section, governed by the D1–… decisions log. Indexed by `IMPLEMENTATION.md` |
| `guide/` | *How to use* silo, for an operator: `configuration.md`, `cli.md`, `http-api.md`, `mcp.md`, `claims.md`, `plugins.md`, `transfer.md`, `deployment.md`, with a `README.md` indexing them |
| `help/` | Long-form, informal walkthroughs. `silo-plugins.md` is the narrative counterpart to `guide/plugins.md` |
| `openapi.json` | The HTTP API as OpenAPI 3.1 — every route, its parameters, its bodies and its responses, for Swagger UI, Redoc and code generators. It sits beside the three directories rather than inside one because it is not prose and has no single audience: an operator points a viewer at it, a client author generates from it, and `docs/guide/http-api.md` links to it. **Hand-written**, because Hono registers routes as code and there is nothing to read them off, so it is a promise the repo makes rather than a derivation — which is why `CLAUDE.md` names it as a mandatory part of any route change and why the file carries its own `x-maintenance` note saying so |

`guide/` exists because the root `README.md` was carrying all of it and had
reached 1,687 lines. A README is a landing page: what silo is, how to install
it, the concepts, and where to read further. Reference material belongs in a
document you can link to a section of, so the README links out to it instead of
inlining it. The split is by *question asked*, which is what keeps the three
directories from drifting into copies of each other: a route's shape is
`guide/`, the reason it has that shape is `design/`, and where the handler lives
is here.
