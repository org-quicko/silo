# Architecture in one minute

> How the pieces fit together today. The design *rationale* is in
> [docs/design/architecture.md](../design/architecture.md).

- **Ports and adapters.** `apps/server/src/core/` defines domain types and the `Storage`/`BlobStorage` interfaces (under `apps/server/src/core/ports/`), importing no adapters; adapters live under `apps/server/src/adapters/`; `apps/server/src/cli/` (`Cli` parses argv, `CommandRouter` routes, `SiloRuntime` wires) wires everything explicitly from config.
- **One process per data directory (D25).** Storage adapters have no cross-process lock and are not meant to: the fs adapter holds `last_seq` in memory and the `ServiceContext` write lock is process-local, which is exactly what lets adapters stay CAS-free. The guard therefore lives at the process boundary — a running server records itself in `<data dir>/silo.run.json` and `serve` refuses to start over a live one. Several instances are fine and expected; each gets its own `--data` and `--listen`.
- **Logging.** Only the long-running server logs, through `Logger` (`apps/server/src/logging/`), to the console and/or a rotating file per `[log]`. Other subcommands write program output to stdout and always will.
- **Document model.** Entries are JSON blobs in an envelope (`id` ULID, `project`, `env`, `collection`, `rev`, `seq`, timestamps) — never schema→table mapping. This keeps storage adapters cheap.
- **Scoping.** A collection is identified by `(project, env, collection)` (D18/D19/D20), where project/env are plain string containers validated by `Scope` (`apps/server/src/core/domain/scope.ts`) — no metadata beyond the two ids. Projects and envs are recorded explicitly (SQLite `projects`/`environments` tables; marker files in the fs adapter) so an empty one can exist, and a scope **exists when it was created explicitly *or* still holds a schema or an entry** — both halves, in both adapters. `Scope.System` (`_system`/`_system`) holds silo-reserved data (`_keys`). `seq` stays instance-global across every scope.
- **Storage adapters:** SQLite (`bun:sqlite` built-in) and filesystem. The fs adapter's on-disk layout **is** the export format (frozen, public, versioned via `format_version`, currently `"2"`) — `projects/<project>/<env>/{schemas,content}/...`.
- **Schemas:** full JSON Schema draft 2020-12, validated server-side via **AJV 2020**. Refs to other collections use `silo://collections/<name>` and resolve only within the same scope; remote `$ref`s are rejected by default (opt-in via `[schema] allow_remote_refs`).
- **Auth:** Shlink-style API keys with claims. A root (`*`) key is generated at first boot. Each protected operation checks one explicit claim, including scoped collection schema/access/entry CRUD (`collections:<project>/<env>/<name>:<permission>`), media, key-management, and transfer claims. Independent per-segment wildcards are supported (e.g. `collections:acme/*/*:entries:read`). `ParsedClaim` validates and enforces non-escalating delegation: a key with `keys:create` can mint only a subset of its own claims, and named segments cannot widen to wildcards. Action wildcards are not accepted. Collection schema and entry reads remain public by default for anonymous requests unless `"x-silo-auth": true` is set. Once a key is presented, its claims are the visibility boundary, so scoped keys do not see unrelated public collections.
- **Plugins (D31–D40).** A package declares what it **contributes** and may contribute several things at once (D36): **providers** implement `Storage` or `BlobStorage` and are constructed in-process before storage opens, each naming its own entry module; hooks, HTTP routes under `/api/ext/{name}/*`, and an `activate`/`deactivate` runtime all run in one `Worker` per plugin, which is what makes `timeout_ms` enforceable. What it *asks for* is split into `required` and `optional` permissions, each carrying the author's reason, and a default grant approves the required half. `silo.toml` says *which* plugins load and in what order — registration, the operator's file, and since D42/D43 the API appends and removes that block itself — and a record in the reserved `_plugins` collection says what each *may do*, so revoking takes effect without a restart and whoever can write the database still cannot execute code. A plugin's `ctx` is one method, `fetch`, dispatched against the **same Hono app** a network request hits with a principal attached under a module-private symbol (D35): `AuthMiddleware` and `RouteAuth` are the authorization path, unchanged, so a plugin is an API key with code attached. Hook *delivery* is its own claim (`hooks:<project>/<env>/<name>:<hook>`), checked in `HookBus` before the event crosses the worker boundary; `collection.afterDelete` is the collection-level one, and the only way a plugin hears about a forced bulk erasure. `PluginRegistry` (`apps/server/src/plugins/registry/`) is the live ordered set and `PluginSupervisor` is the only thing that mutates it — grant, revoke, enable, disable, configure, restart, rescan — with one `PluginAuthority` cell per plugin read by both `HookBus` and `PluginContext`, so authority changes are one assignment (D39). Authority changes are appended to `_audit` by the *services*, so the offline CLI is in the trail too (D38). The admin UI's `Settings → Plugins` (D40) is a client of that API like any other: it renders each plugin's settings form from the manifest's own JSON Schema, and leads every grant with hook delivery, because being handed `entry.beforeValidate` is a larger authority than any `entries:*` permission and reads like a smaller one.
- **Media storage.** Media bytes go through the `BlobStorage` port, resolved by driver name through `ProviderRegistry` like the `Storage` adapters are, so a provider plugin's driver reaches the same lookup `fs` and `s3` do. Since D45 it is also configurable at runtime: `GET`/`PUT /api/media/storage` (behind `media:configure`) and the admin's Settings → Media Library page write the `[blob_storage]` table back into `silo.toml` as text, re-read the config the way a start reads it — flags and `SILO_*` back on top — and open the store from *that*, so what the running process uses is what the next `serve` would compute. The swap is one assignment on `ServiceContext`, which every media call site already reads at the moment it acts; a configuration that cannot be opened restores the file and answers 400. No bytes are moved by a switch, and the admin says so. Since D50 the same is true of the file itself: `ConfigFileAccess` probes whether `silo.toml` can be written before a page offers a form, and a filesystem that refuses the write is a 400 naming the path rather than a 500 naming nothing — the failure being a container, where the config path defaults into an image directory the server's own user cannot write. `SILO_CONFIG` is how such a deployment names the file at all.
- **Media delivery.** Where a media reference resolves to, and what the library accepts, are a second table (`[media]`, D46) behind a second route — `GET`/`PUT /api/media/settings`, the same `media:configure` claim, its own Save on the same page — because a bucket that will not open must not be able to hold up a correction to an allowlist. `base_url_target` decides the URL's shape: `server` keeps silo in the read path and addresses an asset by catalog id, which is what lets `EntryUtils.toApiResponse` stay a pure synchronous function; `store` addresses the blob key, because that is what a bucket serves, and the key lives on the catalog record — so `MediaLinkResolver` resolves it once per response before entries are mapped, and does no I/O at all in the ordinary case. The allowlist is checked on the filename extension rather than the declared content type, before any bytes are written and on rename as well as upload. Both are one assignment on `ServiceContext` for the same reason the blob store is.
- **Server settings.** The rest of `silo.toml` — `[log]`, `[search]`, `[schema]`, `[auth]` — is read and written through `GET /api/settings` and `PUT /api/settings/{table}` behind `settings:configure` (D47), driven by a single spec (`ConfigSections`) that the reader, the writer, the override report and the admin's form all share. It is the first of these that cannot always apply what it saves: a log level is read on every line, while a tokenizer rebuilds an index at boot and a log sink is opened once, so the supervisor keeps the config the process *started on* separate from the file and reports the difference as a restart owed rather than echoing a written value back as in force. `[storage]` is reported and never written, since changing it names a different instance; `[auth] disabled` may only be set to `false`, since an API that can switch off its own authentication is not one.
- **API:** clean routes under `/api`, no URL versioning. JSON everywhere. Collection and entry routes are scoped under `/api/projects/{project}/envs/{env}/collections/...`, with scope listing and creation at `/api/projects`. Optimistic concurrency via `rev` + `If-Match` or `?rev=`. Transfer comes at two blast radii: the whole-instance archive (`/api/export`, `/api/import`, `/api/copy`, gated on instance-wide authority per D21 — the read/write/replace permission lists on `Claims`, with the replace half required only when `mode=replace`) and a scope-to-scope copy (`/api/projects/{project}/envs/{env}/copy`, gated only on the scoped collection claims it exercises — D22).
- **Collection listings carry facts, not schemas (D54).** `GET .../collections` answers `{id, name, entries, requires_auth, created_at, updated_at}` per collection and no schema; `GET .../schemas` answers every schema in the scope for the callers that need the whole graph, and is a sibling of `collections` rather than a path beneath it because `schemas` is a legal collection name. The count comes from `Storage.countEntries(scope)` — a new port method, one `GROUP BY` in SQLite and one directory listing per collection on the filesystem, pinned by the conformance suite — which `ScopeService` uses too. What it replaced everywhere was a `limit=1` list per collection: a whole entry read off disk, and a round trip over HTTP, to learn a number. `GET .../collections/{name}/schema` **bundles on the way out**, re-resolving the `silo://` refs `putSchema` embedded as of its own last save, so one collection's schema is a document a client can render alone — which is what makes fetching every schema unnecessary rather than merely wasteful. It is deliberately not on `CollectionService.get`, which the entry routes call per request to check access.
- **Admin UI state (D53).** The embedded React app keeps **server** state in one store (`apps/admin/src/store/`) and reads it stale-while-revalidate: `Store` holds a `ResourceState` per cache key, `useResource` subscribes to one key through `useSyncExternalStore` and dispatches the load from an effect, so a view renders what the cache has and the request goes out behind it. Cache keys are rooted at the *saved connection's* id rather than the server URL, because a key's claims decide what an answer contains and two saved servers can address one instance with different keys; the store is cleared on disconnect and on a key change. One request per key is in flight at a time, an epoch per key stops a read that started before a write from putting the pre-write answer back, and a failure is state rather than a rejection — which is why a 401 still sends the app to the gate while a request that merely failed does so only when there is nothing cached to show. It is additive: it sits between `api/` and the views, the reads behind every loading screen go through it, and an unconverted read site keeps its own state and works as before. **Client** state stays where it was — the URL is the source of truth for what is on screen, and `localStorage` holds the saved servers, the theme (`ThemeManager`) and per-reader ergonomics like column widths.
