Silo's transfer system moves content between instances, environments, and storage drivers. Every export is streaming — the first bytes leave immediately and no copy of your data is staged on disk first. Archives are reproducible tar.gz files ordered by collection and entry id, byte-for-byte identical from identical data. API key hashes are excluded by default so a content export you share with others ships no credentials.

## Export

Export writes every project and environment, including empty ones, along with schemas, entries, and media. Use `--out` for a compressed archive or `--dir` for an on-disk directory tree.

```bash
silo export --dir ./backup                          # on-disk directory tree
silo export --out backup.tar.gz                     # compressed tarball
silo export --out posts.tar.gz --include acme/prod/posts   # one collection
```

The `--dir` output and the `fs` storage driver share the same layout, so an fs-backed instance is already a live export.

### Narrowing with --include

`--include` narrows an export to a project, an environment, or a single collection. Pass it more than once for multiple scopes. Leave it out for the whole instance.

```bash
silo export --out site.tar.gz --include site                         # one project
silo export --out prod.tar.gz --include site/prod                    # one environment
silo export --out posts.tar.gz \
  --include site/prod/posts --include site/prod/authors              # two collections
```

The same syntax applies on the HTTP route, one `include` parameter per rule:

```bash
curl -H "Authorization: Bearer $SILO_KEY" \
  "http://localhost:8090/api/export?include=site/prod/posts&include=blog" \
  -o partial.tar.gz
```

With no rules, an export requires read permission on everything. With rules, it requires permission only on what the rules name — a key scoped to one project can export that project.

### Controlling media with --media

`--media` (or `?media=` on the HTTP route) controls how media library files are handled:

| Value | Catalog | Files |
|---|---|---|
| `all` | Every asset | Every file in the library |
| `referenced` | Only assets the moved entries point at | Those files only |
| `none` | Every asset | No files — catalog only |

The default is `all` for a whole-instance transfer, and `referenced` once `--include` narrows the scope. Use `none` when both instances share the same S3 bucket — the catalog still moves so filenames, folders, and URLs are preserved, but no bytes are transferred.

### Exporting API keys

Pass `--with-keys` to include API key hashes in the archive. Omit it (the default) for a content export you share with others.

## Import

Import reads an archive or directory and writes its content into Silo. Every imported entry is validated against the schema it lands under — there is no option to skip validation, and a rejected entry is counted and named in the result without stopping the import.

```bash
silo import ./backup --mode merge             # newest updated_at wins
silo import backup.tar.gz --mode replace      # replace per collection
silo import backup.tar.gz --dry-run           # report changes, write nothing
```

### Merge vs replace

<CardGroup cols={2}>
  <Card title="merge (default)" icon="code-merge">
    Matches on `(project, environment, collection, id)`. Missing entries are inserted. Conflicts are resolved by the newest `updated_at`, then by the higher `rev`, then by source `instance_id`. Pass `--prefer local|remote` to override the whole rule.
  </Card>
  <Card title="replace" icon="arrow-right-arrow-left">
    Brings each collection the archive carries to exactly the archive's state. Every entry in the archive is written. Then every entry the archive does not carry is removed. Collections the archive does not mention are left alone.
  </Card>
</CardGroup>

<Note>
  **Deletions do not merge.** Silo keeps no tombstones, so only `replace` mode reflects a deletion made on another instance.
</Note>

<Note>
  **An import is not atomic.** A failure partway leaves earlier writes in place. Treat a failed import as unknown state. A `replace` that stops partway never leaves a collection empty — it writes first and removes after — so the worst case is extra entries. Run the import again to remove them.
</Note>

Check an untrusted archive with `--dry-run` before applying it.

<Note>
  A dry run always reports `rejected: 0`. It does not write schemas, so it has nothing to compare entries against. Use it to preview adds, updates, and schema conflicts — not to audit validation.
</Note>

### Import result shape

```json
{
  "added": 120,
  "updated": 0,
  "deleted": 0,
  "skipped": 0,
  "rejected": 2,
  "rejections": [
    {
      "project": "acme",
      "env": "prod",
      "collection": "posts",
      "id": "01J...",
      "reason": "validation failed: \"/title\": must be string"
    }
  ]
}
```

The `rejections` list holds up to 100 entries. The `rejected` count is always complete. Read it after every import — a source instance can hold data an older schema accepted, and those rows stop at the door.

## Copy between instances

`POST /api/copy` pulls an export from another running Silo and feeds it through the same importer. The destination uses the source credentials for that one request and never stores them.

```bash
curl -X POST http://new-silo:8090/api/copy \
  -H "Authorization: Bearer $DESTINATION_SILO_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "source_url": "http://old-silo:8090",
    "source_api_key": "silo_...",
    "mode": "merge",
    "with_keys": false,
    "dry_run": true,
    "include": ["site/prod"],
    "media": "referenced"
  }'
```

`include` and `media` work the same way as on an export. The destination sends `include` to the source so the source builds only what you asked for rather than the full instance.

## Progress streaming

An import or copy normally says nothing between the request and the answer. Behind a proxy that closes quiet connections, a working transfer can look like a failed one.

Send `Accept: application/x-ndjson` to receive one JSON object per line as work progresses:

```bash
curl -X POST "http://new-silo:8090/api/import" \
  -H "Authorization: Bearer $DESTINATION_SILO_KEY" \
  -H "Accept: application/x-ndjson" \
  -H "Content-Type: application/gzip" \
  --data-binary @backup.tar.gz
```

```
{"type":"progress","phase":"extract","result":{...}}
{"type":"progress","phase":"entries","result":{"added":200,...}}
{"type":"progress","phase":"media"}
{"type":"result","result":{"added":412,"updated":0,...}}
```

The stream sends a `progress` line whenever the importer reports (every 200 entries and at each phase boundary), a bare heartbeat after each second of silence, and a final `result` or `error` line. The **HTTP status goes out before the work begins** — the first byte is the status line, and the outcome is the last line.

<Warning>
  **Read the last line, not the HTTP status code.** The status is sent before work starts, so it is always `200`. A failure arrives as an `error` line:

  ```
  {"type":"error","status":409,"error":{"code":"conflict","message":"..."}}
  ```

  A stream that stops with no `result` line means the connection ended before the transfer finished. The destination is in an unknown state — check it before retrying.
</Warning>

The admin UI's **Data Transfer** page uses this stream to show live progress for running imports and copies.

## Copying between environments on the same instance

Moving data between two environments on the same instance requires no archive. Promoting `dev` to `staging`, or seeding a fresh environment from `prod`, is a single request:

```bash
curl -X POST http://localhost:8090/api/projects/acme/envs/staging/copy \
  -H "Authorization: Bearer $SILO_KEY" \
  -H "Content-Type: application/json" \
  -d '{"from": {"project": "acme", "env": "prod"}, "mode": "merge", "dry_run": true}'
```

```json
{
  "mode": "merge",
  "dry_run": true,
  "added": 12,
  "updated": 0,
  "deleted": 0,
  "skipped": 3,
  "rejected": 0,
  "rejections": []
}
```

This route requires **no `transfer:*` claim**. It uses the same collection and entry claims as the ordinary CRUD routes:

| Direction | Claim required |
|---|---|
| Source read | `collections:<project>/<env>/*:schema:read`, `collections:<project>/<env>/*:entries:read` |
| Destination write | `collections:<project>/<env>/*:create`, `collections:<project>/<env>/*:schema:update`, `collections:<project>/<env>/*:entries:create`, `collections:<project>/<env>/*:entries:update` |
| Replace mode (delete) | `collections:<project>/<env>/*:delete`, `collections:<project>/<env>/*:entries:delete` |

A key scoped to one project can move data between that project's environments and no others. Copying an environment onto itself is a `400`. Media is stored per instance, not per environment, so it is already shared and none is copied.

The admin exposes this at **Settings > Environment > Data Transfer** with a preview-then-apply flow.

## Copy an environment from another instance

Promote content from one instance to the next, such as `acme/dev` on your dev server into `acme/uat` on your uat server, or refresh a lower stage from prod. The two environments can have different names. Only the collections and entries you pick leave the source, with the media files they use.

A copy between instances runs in three steps on the destination:

<Steps>
  <Step title="Prepare">
    The destination pulls a package from the source that holds exactly your selection, checks it, and plans it against its own content. Nothing is written.
  </Step>
  <Step title="Review">
    Page through the plan: every entry and media file the copy adds, updates, skips or deletes, and the packaged copy of any entry.
  </Step>
  <Step title="Apply">
    The destination writes the plan as one change. If anything the plan read has changed since, it writes nothing and answers `409 stale_preview`. Prepare again.
  </Step>
</Steps>

The review and Apply use the saved package and never read the source again, so edits on the source after Prepare do not shift what you reviewed. The source must run Silo 1.6.0 or later. The destination must use the SQLite or Postgres driver; the `fs` driver answers `409 atomic_commit_unsupported`.

### In the admin

On the destination, open **Settings > Environment > Data Transfer** and pick the source in **Source server** (any other server saved in the admin). Paste a source key: it is used for this copy only and never saved. Pick the environment and what to copy, then **Preview copy** and **Apply copy**. A preview is cancelled when you change an input or leave the page.

The browser reads the source to list its projects and collections, so use a source URL that both the browser and the destination server can reach.

### Over HTTP

```bash
curl -X POST https://uat.example.com/api/projects/acme/envs/uat/transfers \
  -H "Authorization: Bearer $UAT_SILO_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "source": {"url": "https://dev.example.com", "api_key": "silo_..."},
    "from": {"project": "acme", "env": "dev"},
    "selection": [{"collection": "posts"}, {"collection": "pages", "entry_ids": ["01J8XQ4Z8K9M2P3R5T7V9X1B3D"]}],
    "mode": "merge",
    "media": "referenced"
  }'
```

The answer is `201` with the transfer: its `review` totals and the first page of the plan. Then, with the same key:

| Request | Does |
|---|---|
| `GET …/transfers/{id}?detail_offset=25` | The next page of the plan |
| `GET …/transfers/{id}/entries/{collection}/{entry}` | The copy of one entry that Apply writes |
| `POST …/transfers/{id}/apply` | Writes the plan as one change, or nothing |
| `DELETE …/transfers/{id}` | Cancels the transfer |

Prepare and Apply both stream progress with `Accept: application/x-ndjson`. The first line names the transfer, so you can cancel while the destination is still pulling.

### What to know

- **Keys.** The source key needs `transfer:export` and `schema:read` plus `entries:read` on the source environment. Give it nothing else. The destination key needs `transfer:copy` and the same write claims as a copy between environments, plus the replace claims in `replace` mode and `media:create` unless `media` is `none`.
- **Media.** `referenced` (the default) brings the files the selected entries use; `none` brings no files and no media records. An asset the destination lacks is added. An asset it already has is never changed or deleted, even in `replace` mode: if the bytes or details differ, the plan shows it as skipped with the reason. References that will not resolve on the destination are listed in the plan.
- **What stays behind.** Variables and API keys never move. Each instance keeps its own.
- **Limits.** A prepared transfer expires after 60 minutes. A server holds at most 4 open transfers; the next is `429 too_many_transfers`.
- **Retries.** Apply on an applied transfer answers it again with `200` and writes nothing. Only the key that prepared a transfer can read, apply or cancel it. If the server stops mid-Apply, it settles that Apply when it starts again.

<Warning>
  **Treat `transfer:copy` as a powerful claim.** The destination sends a request to whatever `source.url` names, and Silo does not limit which addresses it may reach, including ones on your private network. Give `transfer:copy` only to the people who release content, and restrict the server's outbound traffic with firewall rules.
</Warning>

## HTTP API reference

| Action | Endpoint |
|---|---|
| Export | `GET /api/export` |
| Import | `POST /api/import` |
| Copy from another instance | `POST /api/copy` |
| Copy between environments | `POST /api/projects/{p}/envs/{e}/copy` |
| Send a transfer package (the source half) | `POST /api/projects/{p}/envs/{e}/package` |
| Prepare a transfer from another instance | `POST /api/projects/{p}/envs/{e}/transfers` |
| Read, apply, or cancel it | `GET`, `POST …/apply`, `DELETE` on `/api/projects/{p}/envs/{e}/transfers/{id}` |

## Required claims

| Operation | Claims required |
|---|---|
| `transfer:export` | Also needs `collections:*/*/*:schema:read` and `collections:*/*/*:entries:read` (or narrowed equivalents) |
| `transfer:import` | Also needs `entries:create`, `entries:update`, `entries:delete` on the destination scope |
| `transfer:copy` | Requires both `transfer:export` authority on the source and `transfer:import` authority on the destination |
| Transfer package (source) | `transfer:export`, plus `schema:read` and `entries:read` on each packaged collection |
| Prepare and apply a transfer (destination) | `transfer:copy`, plus the environment copy's write claims on each collection, its replace claims in `replace` mode, and `media:create` unless `media` is `none` |

## Archive format and on-disk layout

The on-disk layout produced by `--dir` and the `fs` storage driver are one and the same format. Every archive and every fs-backed instance carries a `format_version` — currently `"1"`. Silo refuses to open or import data stamped with a version it does not recognize.

```
<data-dir>/
  manifest.json                 # format_version, instance_id, last_seq,
                                # selection and media scope if narrowed
  projects/
    acme/
      prod/
        schemas/
          posts.schema.json
        content/
          posts/
            01J8XQ4Z8K9M2P3R5T7V9X1B3D.json
  media/
```

Each entry file holds the full envelope, pretty-printed with a stable field order so diffs stay small. The same collection name in two environments never collides, on disk or in an archive.

## Size limits

Archives arriving over HTTP are checked twice before anything is written:

| Setting | Default | What it limits |
|---|---|---|
| `[transfer] max_archive_size_mb` | 1024 MB | The compressed archive size |
| `[transfer] max_extracted_size_mb` | 4096 MB | The uncompressed size (read from archive headers; every file counts as at least 4 KB) |

A request past either limit gets a `413` with code `archive_too_large`. The message names the setting to raise. Both limits apply to `/api/import` and `/api/copy`. A file you name on the command line is not checked.

Raise both to copy a large instance. Both are configurable in `silo.toml` or from **Settings > Configuration > Transfers** in the admin.

## Importing system records

An archive can carry Silo's own records under `_system`. A selection cannot name them, so the import checks them after unpacking, against the same claims their own routes require:

| Records | Claim needed |
|---|---|
| `_keys` | `keys:import` |
| `_media`, `_media_folders`, `_media_folder_moves` | `media:create` (even with `media=none`); `media:delete` too when `replace` would empty them |
| `_variables` for a project | `create` and `entries:update` on `<project>/*/*` |
| `_audit`, `_plugins`, `_transfers` | Only by `silo import` on the host, from an archive made with `silo export --instance`. Over HTTP the request is a `403` |
| `_scope_renames`, any other `_` name | Never imported. The request is a `400` |

A missing claim is a `403` that names the records and the claim. The check reads rows, not empty collections, so exporting an empty library loads with content permissions alone. The `silo import` CLI on the host is trusted and loads all of it.

## Cross-driver migration

Export and import speak only the storage interface, so switching from SQLite to the `fs` driver (or back) is:

```bash
silo export --out migration.tar.gz          # from the old instance
silo import migration.tar.gz --mode replace # into the new one
```

This is also the acceptance test for any third-party storage driver — both drivers must produce identical API results.
