# 1.6.0

silo 1.6.0 adds two features: copying an environment from another silo
instance, and a trash that keeps deleted content for 30 days.

## New: copy an environment from another instance

Promote content from one silo instance to another. For example, copy
`acme/dev` on your dev server into `acme/uat` on your uat server, or refresh a
lower stage from prod. The two environments can have different names.

- **Only what you pick leaves the source.** The source sends a package with the
  selected collections and entries and the media files they use. Variables,
  keys and everything else stay where they are.
- **You review before anything is written.** The destination checks the
  package and saves a plan: each entry and media file it will add, update, skip
  or delete.
- **Apply writes exactly that plan, or nothing.** The plan is written as one
  change. If the destination changed after the review, Apply writes nothing and
  answers `409 stale_preview`. Prepare the transfer again and review the new
  plan.
- **Existing media is never changed.** A file the destination lacks is added. A
  file it already has is never changed or deleted, even in replace mode.
- **A retry is safe.** Applying twice writes once. If the server stops during
  an apply, it completes or undoes that apply when it starts again.

**In the admin:** on the destination, open **Settings > Environment > Data
Transfer**, choose the other server in **Source server**, and paste a source
key. silo uses the key for that copy only and does not save it.

**Requirements:**

- silo 1.6.0 on both instances.
- SQLite or Postgres storage on the destination. The fs driver answers
  `409 atomic_commit_unsupported`.
- On the source, a read-only key with `transfer:export`, plus `schema:read` and
  `entries:read` on `collections:<project>/<env>/*`.
- On the destination, a key with `transfer:copy` and write claims on the
  destination environment, plus `media:create` when media files come along.

**API:** the source answers `POST …/envs/{env}/package`. The destination adds
`POST …/envs/{env}/transfers`, and `GET`, `DELETE` and `POST …/apply` on
`…/transfers/{id}`. New error codes: `stale_preview`, `transfer_expired`,
`transfer_in_progress`, `transfer_cancelled`, `transfer_applied`,
`atomic_commit_unsupported` and `too_many_transfers` (`429`). A prepared
transfer expires after 60 minutes, and a server holds at most 4 at once.

The full guide is in
[transfer.md](https://github.com/org-quicko/silo/blob/v1.6.0/resources/guide/transfer.md#copying-an-environment-from-another-instance).

## New: the trash

Deleting a project, an environment, a collection, an entry, a media file or a
media folder now moves it to the trash. You can restore it for 30 days.

- **One item per delete.** A collection deleted with 300 entries is one item.
  A restore brings all 300 back.
- **A restore puts content back where it was**, even after a rename. If that
  place no longer exists, the restore stops and names it. If that place is in
  the trash too, you can restore both in one step. If the name is taken, or a
  restored entry no longer fits its collection's schema, the restore answers
  `409` and the item stays in the trash.
- **Undo in the admin.** Deleting an entry shows an undo button. The new
  **Trash** page, below **Media Library** in the sidebar, lists deleted items
  newest first, a page at a time.
- **Each key sees only what it could read.** The trash shows a key only the
  deleted items it could read before. A restore needs write claims where the
  content goes back.
- **Delete for good with `trash:purge`.** This new claim purges one item,
  empties the trash, and allows `?permanent=true` on any delete route, which
  skips the trash. Only `root` keys hold it.
- **Settings:** `[trash] enabled` (default `true`; `false` deletes at once, as
  before) and `retention_days` (default 30; `0` keeps items until someone
  purges them). `SILO_TRASH_ENABLED` takes only `true` or `false`. An item's
  expiry is set when it is deleted, so a shorter setting later does not remove
  it early.

**API:** `GET /api/trash`; `GET`, `DELETE` and `GET …/items` on
`/api/trash/{id}`; `POST /api/trash/{id}/restore`; and `POST /api/trash/purge`.
A `DELETE` on an entry, a media file or a media folder also answers an
`X-Silo-Trash-Id` header, and `GET /api/session` says whether the trash is on.

The full guide is in
[trash.mdx](https://github.com/org-quicko/silo/blob/v1.6.0/docs/guides/trash.mdx).

## Clients

The TypeScript, Java and Dart clients are now 1.6.0. All three have
`silo.trash` (`silo.trash()` in Java). `delete()` on an entry or a media file
returns the trash item's id, or `null` when nothing was kept (an empty
`Optional` in Java).

**Breaking change in the Java client.** `delete()` returned `void` and now
returns `Optional<String>`. Source code still compiles, but code built against
an earlier client fails at run time with `NoSuchMethodError` until you rebuild
it.

## Fixes

- **Imported media keeps its type and download name.** An import or a server
  copy wrote media files with no content type, so a bucket in front of silo
  served SVGs that did not draw. To repair a library imported before 1.6.0, run
  `silo media rekey --rewrite`.
- **A wrong source key no longer logs you out.** On
  **Settings > Data Transfer > Copy from silo**, a refused source key
  disconnected the admin. It now shows *The source refused this key.* under the
  field.
- **A narrowed server copy is no longer sent whole.** On the same tab, a copy
  with only some collections checked could go out as the whole source when the
  source's collection list failed to load. Preview now waits for the list.
- **A saved server with a refused key opens in an edit dialog**, so you can
  replace the key without clearing the browser's storage.

## Other changes

- SQLite and Postgres storage can apply many writes as one change. Media files
  on local disk are flushed to disk before an upload returns, so a file that
  exists after a power cut is complete.
- `_transfers` is a new system collection that records each applied transfer.
  Like `_audit`, it moves only with `silo export --instance`. No export carries
  the trash.
- The public documentation site is in `docs/`. The internal design and guide
  documents moved to `resources/`.
