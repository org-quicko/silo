## Read this before you upgrade

**`transfer:copy` now opens a second way for your server to call any address.**

A key that holds `transfer:copy` could already make the server fetch from a URL
the caller names, through `POST /api/copy`. 1.6.0 adds a second route that does
the same, `POST /api/projects/{project}/envs/{env}/transfers`, and this one
also sends a JSON body. silo does not limit which addresses either route may
reach, so a `transfer:copy` key can point your server at an address on your
private network.

Before you upgrade:

1. Find every key that holds `transfer:copy`. In the admin, open
   **Settings > API Keys** and read each key's claims, or call `GET /api/keys`.
2. Keep `transfer:copy` only on the keys of the people who release content.
   Remove it from every other key.
3. Limit the server's outbound connections with firewall rules, so it can reach
   only the silo instances it copies from.

**A delete now goes to the trash, and stays there for 30 days.** Deleting a
project, an environment, a collection, an entry or a media file no longer
removes the data from storage at once. If you must remove data at once, for
example for a privacy request:

1. Delete with `?permanent=true`, using a key that holds the new `trash:purge`
   claim. Only `root` keys hold it.
2. Or set `[trash] enabled = false` in `silo.toml` to keep the old behaviour.
   A test instance that creates and drops data all day can do the same.

**Nothing else changes for existing setups.** Every key keeps its meaning: a
delete asks for the same claims as before. Routes keep their shape, and
exports, imports and copies work as they did. Your data needs no migration: the
new `_transfers`, `_trash` and `_trash_items` system collections are created
the first time 1.6.0 starts.

## New: copy an environment from another instance

Promote content from one silo to the next, for example `acme/dev` on your dev
server into `acme/uat` on your uat server, or refresh a lower stage from prod.
The two environments can have different names.

- **Only what you pick leaves the source.** The source builds a package with
  the collections and entries you selected and the media files they use.
  Variables, keys and everything else stay where they are.
- **Review first.** The destination checks the package and saves a plan: each
  entry and media file it would add, update, skip or delete. Nothing is written
  yet.
- **Apply writes exactly that plan, or nothing.** The plan is written as one
  change. If the destination changed after the review, Apply writes nothing and
  answers `409 stale_preview`, so you review again.
- **Existing media is never touched.** A file the destination lacks is added. A
  file it already has is never changed or deleted, even in replace mode.
- **Safe to retry.** Applying twice writes once. If the server stops during an
  apply, it finishes or undoes that apply when it starts again.

**In the admin:** on the destination, open **Settings > Environment > Data
Transfer**, pick the other server in **Source server**, and paste a source key.
The key is used for that copy only and never saved.

**What you need:**

- silo 1.6.0 on both instances.
- SQLite or Postgres storage on the destination. The fs driver refuses with
  `409 atomic_commit_unsupported`.
- On the source, a read-only key with `transfer:export` and
  `collections:<project>/<env>/*:schema:read` and `entries:read`.
- On the destination, a key with `transfer:copy` and write claims on the
  destination environment, plus `media:create` when media files come along.

Read the full guide in
[transfer.md](https://github.com/org-quicko/silo/blob/v1.6.0/resources/guide/transfer.md#copying-an-environment-from-another-instance).

New routes: `POST …/envs/{env}/package` on the source, and on the destination
`POST …/envs/{env}/transfers` plus `GET`, `DELETE` and `POST …/apply` on
`…/transfers/{id}`. New error codes: `stale_preview`, `transfer_expired`,
`transfer_in_progress`, `transfer_cancelled`, `transfer_applied`,
`too_many_transfers` (`429`) and `atomic_commit_unsupported`. A prepared
transfer expires after 60 minutes, and a server holds at most 4 open at once.

## New: the trash

Deleting a project, an environment, a collection, an entry, a media file or a
media folder moves it to the trash. You can restore it for 30 days.

- **One item per delete.** A collection deleted with 300 entries is one item,
  and a restore brings all 300 back.
- **A restore puts it back where it was**, even if a project or environment
  was renamed since. If the place it goes back to is gone, the restore stops
  and names it. If that place is in the trash too, you can restore both in one
  step. If the name is taken, the restore answers `409`.
- **Undo in the admin.** Deleting an entry shows an undo button. The new
  **Trash** page, under **Media Library**, lists what was deleted, newest
  first.
- **A key sees only what it could read.** The trash shows each key the deleted
  items it could read before. A restore needs write claims where the item goes
  back.
- **Delete for good with `trash:purge`.** This new claim deletes one item for
  good, empties the trash, and allows `?permanent=true` on any delete route.
  Only `root` keys hold it.
- **Settings:** `[trash] enabled` (on) and `retention_days` (30; `0` keeps
  items until someone deletes them). An item's expiry is set when it is
  deleted, so a shorter setting later does not remove it early.

New routes: `GET /api/trash`, `GET`, `DELETE` and `GET …/items` on
`/api/trash/{id}`, `POST /api/trash/{id}/restore` and `POST /api/trash/purge`.
`DELETE` on an entry or a media file also answers an `X-Silo-Trash-Id` header,
and `GET /api/session` now says whether the trash is on. The TypeScript client
has `silo.trash`, and `delete()` on an entry or a media file returns the trash
item's id.

## Fixes

- **Imported media keeps its type and download name.** An import or a server
  copy wrote media files with no content type, so a bucket in front of silo
  served SVGs that did not draw. Run `silo media rekey --rewrite` to repair a
  library imported before 1.6.0.
- **A wrong source key no longer logs you out.** On **Settings > Data
  Transfer > Copy from silo**, a refused source key used to disconnect the
  admin. It now shows *The source refused this key.* under the field.
- **A narrowed server copy is no longer sent whole.** On the same tab, a copy
  with only some collections checked could be sent as the whole source when
  the source's list failed to load. Preview now waits for the list.
- **A saved server with a refused key opens in an edit dialog**, so you can
  replace the key without clearing the browser's storage.

## Also in this release

- SQLite and Postgres storage can apply many writes as one change. Media files
  on local disk are flushed before an upload returns, so a file that exists
  after a power cut is complete.
- `_transfers` is a new system collection that records each applied transfer.
  Like `_audit`, it moves only with `silo export --instance`.
- The trash never moves: no export carries it, not even
  `silo export --instance`. Restore or empty what you need before you move an
  instance to another driver or machine.
- The public documentation site now lives in `docs/`, and the internal design
  and guide documents moved to `resources/`.
